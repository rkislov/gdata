# GData SRK

Распределенная система резервного копирования на Go с веб-интерфейсом Tailwind CSS.

Автор: **Кислов Роман Сергеевич**. Лицензия: **Apache License 2.0**. Исходники: [github.com/rkislov/gdata](https://github.com/rkislov/gdata). Предложения и ошибки принимаются через Issues и Pull Requests; изменения принимает владелец.

Версия 0.9.2 добавляет Linux flash/USB-тома с UUID, автономные копии, кэш каталога отключённого носителя и release/attach. [Настройка и ограничения](docs/removable.md).

Версия 0.9.0 добавляет ленточный эмулятор: управление кассетами, маркировку, стирание и подготовку к перезаписи, автономные копии и восстановление, удержание, CLI и веб-интерфейс. Linux SCSI-транспорт реализует робототехнику, запись, восстановление, импорт и защищённую подготовку к перезаписи; [конфигурация и ограничения](docs/scsi-v091.md). [Инструкция](docs/tape-v09.md).

Версия 0.8.2 добавляет постоянную защиту WAL на источнике до подтверждения всех приёмников и отображение отставания в интерфейсе. Пауза сохраняет защиту; явное снятие доступно администратору через API/CLI с причиной и аудитом.

Версия 0.8.1 добавляет непрерывную репликацию WAL, политики синхронизации, SHA-256, прогресс/журнал и календарь PITR приёмника. Проверено восстановление на заданное время с удалённого архива на настоящем PostgreSQL 16. [Инструкция](docs/wal-replication.md).

Версия 0.8 добавляет прямую репликацию копий между медиасерверами: SHA-256, независимое хранение, очередь, прогресс и журнал в веб-интерфейсе. [Настройка и ограничения](docs/replication-v08.md).

Версия 0.7 добавляет управление бэкапом и восстановлением ВМ OpenStack/Tionix и oVirt в веб-интерфейсе, S3-источник MinIO/Ceph и логические дампы MySQL/MariaDB. Дедупликация, защищённая связь, очередь и журнал общие для всех источников. Подробности настройки и ограничения: [docs/sources-v07.md](docs/sources-v07.md). Добавлены HTTPS-бэкап и восстановление Proxmox без PBS через WebDAV СРК и OpenNebula 7.4 через OneBEX: [настройка и ограничения](docs/proxmox-opennebula.md).

## Что работает

- Управление заданиями и устойчивой очередью в PostgreSQL, ручные и интервальные запуски, отмена, ограничения параллельности по системе, агенту и медиасерверу.
- Агентское файловое копирование на дисковый медиасервер: блоки по 4 МиБ, SHA-256, дедупликация, самодостаточные манифесты, проверка перед публикацией и резерв свободного места 1 ГиБ по умолчанию (`reserve_bytes`).
- Полный и последующие инкрементальные/дифференциальные проходы с полным чтением источника и передачей отсутствующих блоков. В манифесте сохраняется baseline; восстановление не требует чтения предыдущего манифеста.
- Восстановление в новый разрешенный каталог с проверкой хешей, прав доступа и времени изменения; каталоги, обычные файлы, пустые файлы и внутренние символические ссылки.
- mTLS с TLS 1.3, идентификаторы компонентов в сертификатах, проверка роли и ID сервера, ограниченные по времени права на поток данных, отзыв сертификатов с проверкой на каждом запросе.
- Парящие плитки, текущая активность, история с фильтрами и страницами, ближайшие запуски, задания, хранилища, компоненты и аудит. CSV и XLSX, включая планируемые запуски при соответствующем выборе области отчета.
- Горячий PostgreSQL через именованные профили агента: полная физическая копия с WAL, нативная проверка и восстановление в новый каталог. [Настройка PostgreSQL](docs/postgresql.md).
- Непрерывное архивирование завершенных WAL через ограниченный `archive_command`, связь с кластером и изолированное PITR до заданного времени. [Настройка WAL/PITR](docs/wal-pitr.md).
- CPU, RAM, тома, дисковый I/O и сетевые скорости; проценты этапов задания и экономия дедупликации. [Как считаются показатели](docs/statistics.md).
- CLI для управления, медиасервера, агента и прокси; роли администратора и аудитора по сертификатам; вход администратора в веб-интерфейс по паролю.
- Удержание точек, изменение сроков, предварительный расчет очистки, защита активных потоков, восстановление журнала очистки и импорт собственного дискового формата. [Инструкция по жизненному циклу](docs/lifecycle.md).

Файловый агент читает живое дерево (`consistency: live-files`); изменение читаемого файла приводит к ошибке, общего снимка файловой системы нет. OpenStack/Tionix и oVirt используют отдельные адаптеры снимков/экспорта. Proxmox использует HTTPS/WebDAV-монт на узлах PVE; OpenNebula — OneBEX за HTTPS-прокси и защищённый импорт образов. Требуется предварительная настройка инфраструктуры по [инструкции](docs/proxmox-opennebula.md). Ленты остаются на этапе безопасного планирования. Промышленная приёмка реальных гипервизоров и целевых ОС ещё необходима.

## Локальный запуск

Нужны Go 1.26+, PostgreSQL с утилитами `initdb`, `pg_ctl`, `createdb`, `psql` и POSIX shell. Для пересборки CSS нужны Node.js и npm; готовый CSS уже включен в исходники и Go-бинарник.

```sh
make build
bin/srk dev init
make postgres
sh scripts/dev-services.sh
```

`dev init` создает `.local/` с конфигурациями, ключами, отдельным CA, случайным паролем администратора, примером задания и тестовым источником. Повторный запуск отказывается перезаписывать существующую инсталляцию. Все четыре сервиса запускаются локально:

- Система управления и веб-интерфейс: `https://localhost:8443`.
- Медиасервер: `https://localhost:8444`.
- Файловый агент: `https://localhost:8445`.
- Прокси: `https://localhost:8446`.

Для браузера необходимо доверие к созданному локальному CA `.local/pki/ca.crt`. Пароль находится в `.local/admin.password`; он не выводится при запуске. CLI уже доверяет этому CA по конфигурации. Приватный ключ CA не переносится на рабочие агенты и медиасерверы.

Кластер PostgreSQL для разработки создается исключительно в `.local/postgres`, слушает `127.0.0.1:55432` и использует `trust` для локального стенда. Для промышленной конфигурации проверка требует `sslmode=verify-full`; исключение допускается только с `development: true` для loopback-адреса.

`Ctrl+C` в скрипте сервисов завершает четыре компонента. PostgreSQL можно остановить отдельно:

```sh
pg_ctl -D .local/postgres -m fast stop
```

## Первая копия и восстановление

После появления компонентов создайте задание через интерфейс или CLI:

```sh
bin/srk --config .local/admin.json --json manager jobs create --file .local/example-job.json
bin/srk --config .local/admin.json --json manager jobs list
bin/srk --config .local/admin.json --json --wait --timeout 5m manager jobs run JOB_ID
bin/srk --config .local/admin.json --json manager runs list
bin/srk --config .local/admin.json --json --wait --timeout 5m manager runs verify RUN_ID
bin/srk --config .local/admin.json --json --wait --timeout 5m manager runs restore RUN_ID --destination /absolute/path/to/gdata/.local/restores/recovery-001
```

Замените `JOB_ID`, `RUN_ID` и абсолютный путь реальными значениями. Назначение восстановления должно входить в `restore_roots` агента и не должно существовать. Рабочие файлы автоматически не перезаписываются. Все глобальные флаги CLI указываются **перед** компонентом.

Для PostgreSQL-копии, связанной с архивом WAL, команда восстановления дополнительно принимает `--target-time RFC3339` и необязательный `--exclusive`. Успешный PITR означает достижение цели и остановленный кластер в новом каталоге; параметры публикации задаются отдельно.

`--wait` ожидает завершения операции. Без него код 0 означает принятие в очередь. Истечение времени ожидания не отменяет серверное задание; отмена выполняется командой `manager runs cancel RUN_ID`.

## CLI компонентов

```sh
bin/srk help
bin/srk --config .local/manager.json manager check-config
bin/srk --config .local/media.json media status
bin/srk --config .local/agent.json agent health
bin/srk --config .local/proxy.json proxy status
bin/srk --config .local/admin.json --endpoint https://localhost:8444 media verify RUN_ID
bin/srk --config .local/admin.json manager report --format xlsx --out operations.xlsx
bin/srk --config .local/auditor.json --json manager audit
```

Диагностические команды с конфигурацией самого компонента используют его сертификат. Для административных операций применяется клиентский сертификат администратора. Локальный Unix-сокет управления пока не реализован: CLI обращается к сервисам по mTLS.

Для повтора запроса запуска с тем же результатом можно задать глобальный `--idempotency-key KEY`. Запуск, восстановление и проверка повторно вернут ту же операцию; ключ нельзя использовать для другого назначения восстановления.

Коды возврата: 0 — успех, 1 — ошибка операции, 2 — аргументы/конфигурация, 3 — отказ прав, 4 — недоступность сервиса или тайм-аут, 5 — конфликт состояния. JSON в stdout не содержит ANSI-последовательностей; сообщения об ошибках направляются в stderr.

## Разработка и проверки

```sh
make css
make test
```

`make build-linux` собирает `bin/srk-linux-amd64` без CGO. Это проверка сборки под Linux, а не подтверждение испытаний на ALT/ROSA. Пример systemd-unit находится в `packaging/systemd/srk@.service`; перед использованием нужно создать сервисного пользователя, настроить пути и разрешения источников. Unit ограничивает доступ к домашним каталогам и запись вне `/var/lib/srk` и `/var/log/srk`.

Для интеграционных тестов используйте **отдельную** PostgreSQL-базу. Тесты создают изолированные схемы и удаляют их после завершения. База должна разрешать `CREATE SCHEMA`; работающая инсталляция СРК в ней не допускается.

```sh
createdb -h 127.0.0.1 -p 55432 srk_test
SRK_TEST_DATABASE_URL='postgres://YOUR_USER@127.0.0.1:55432/srk_test?sslmode=disable' go test -race -count=1 -timeout 180s ./...
```

Без этой переменной интеграционные тесты с PostgreSQL пропускаются; файловые, криптографические и HTTP/mTLS-тесты выполняются. Зависимости закреплены `go.sum` и `package-lock.json`. Проверка браузера проводилась на локальном стенде; аппаратная совместимость ALT/ROSA и ленточных устройств этим не подтверждается.

## Структура

`cmd/srk` — CLI и запуск сервисов; `internal/catalog` — PostgreSQL; `internal/service` — API, планировщик, агент и медиасервер; `internal/repository` — блочное хранилище; `internal/identity` — сертификаты и права на потоки; `internal/web` — встроенный интерфейс; `internal/report` — XLSX и защита CSV; `docs` — API и границы реализации.
