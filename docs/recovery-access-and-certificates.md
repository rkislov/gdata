# Целевые площадки восстановления и персональные сертификаты

## Авторизация восстановления

У оператора независимо проверяются:

1. Разрешение restore.
2. Исходная область: пересечение job_ids/all_jobs и site_ids/all_sites. Площадка источника берётся из политики защиты задания.
3. Целевая область: restore_site_ids или all_restore_sites.
4. Выбранная административная привязка restore_target_id к зарегистрированному агенту/прокси, типу источника и профилю.

Пустой список целевых площадок при выключенном all_restore_sites запрещает восстановление. Глобальная исходная область сама по себе не разрешает целевые площадки. Для операторов restore_target_id обязателен; передать произвольный site_id вместо зарегистрированной цели нельзя. Администратор сохраняет ручное восстановление без привязки; при выборе цели даже администратор использует её утверждённые параметры.

В веб-интерфейсе администратор создаёт площадки в «Защита 3-2-1», затем задаёт привязки в «Цели восстановления» и разрешает целевые площадки в карточке пользователя. В истории у администратора есть кнопка «На целевую площадку»; у оператора обычное восстановление открывает выбор разрешённых целей.

Привязки сохраняются в restore_targets существующих ProtectionSettings с контролем версии. Пример элемента:

```json
{
  "id": "remote-files",
  "name": "Файловый сервер на резервной площадке",
  "site_id": "remote",
  "node_id": "recovery-agent",
  "kind": "files"
}
```

Типы: files, postgresql, s3, mysql, kubernetes, longhorn, openstack, ovirt, proxmox, opennebula. Для файлов и PostgreSQL профиль не задаётся: один агент и все его restore_roots относятся к одной физической площадке. Путь назначения должен быть абсолютным и каноническим; ограничения файловой системы продолжает применять агент. Для S3, MySQL, Kubernetes и Longhorn profile должен совпасть с профилем URI назначения. Целевой агент должен иметь нужный профиль, разрешение восстановления и доступ к данным; Longhorn по-прежнему требует доступного внешнего backupstore.

Для ВМ дополнительно задаётся vm — шаблон VMRestoreRequest с flavor_id, networks и необходимыми для платформы параметрами хранилища/размещения. Имя новой ВМ вводит оператор. Сервер устанавливает proxy_id и profile из привязки, остальные параметры размещения — из шаблона. Переданные пользователем сети, профиль, прокси, зона и хранилища не заменяют шаблон.

Привязка — административное описание физического расположения. Один агент файлового восстановления нельзя назначить одновременно разным площадкам. Одинаковый профиль одного типа на одном узле также нельзя связать с разными площадками. При изменении endpoint профиля или физическом переносе узла администратор должен актуализировать привязку. Профили, охватывающие несколько площадок, необходимо разделить; для ВМ дополнительно фиксируется размещение в шаблоне.

Операция сохраняет restore_target_id, restore_site_id и фактический целевой узел; журнал содержит restore.target.authorized или restore.target.denied. Изменение прав влияет на новые запросы. Уже принятые операции выполняются с зафиксированными параметрами.

Восстановление с ленты в дисковый репозиторий требует глобальной исходной области, restore и разрешения площадок всех зарегистрированных дисковых репозиториев выбранного медиасервера. Неизвестное размещение запрещает операцию. Выдача кодов SRK Rescue и настройка автоматических проверок остаются административными действиями.

### CLI

```sh
bin/srk --config admin.json manager protection settings
bin/srk --config admin.json manager protection put --file protection-settings.json
bin/srk --config operator.json manager restore-targets
bin/srk --config operator.json manager runs restore RUN_ID --restore-target remote-files --destination /srv/restore/new-copy
bin/srk --config operator.json manager runs restore RUN_ID --restore-target remote-vm --vm-request vm-name.json
```

Для утверждённой цели ВМ vm-name.json может содержать только `{"name":"recovered-vm"}`. Для PostgreSQL дополнительно поддерживается существующий --target-time. Для Kubernetes назначение имеет вид kubernetes://PROFILE/SOURCE_NAMESPACE/NEW_NAMESPACE?start=false.

## Управляемые персональные сертификаты

Управление доступно администратору: «Пользователи» → «Сертификаты» или CLI manager certificates. Закрытый ключ создаётся на компьютере пользователя и не передаётся менеджеру. Сервер получает подписанный CSR, проверяет его подпись и выпускает сертификат только роли user с идентификатором выбранной учётной записи, текущей инсталляцией и назначением TLS ClientAuth. Идентичности, DNS-имена и расширения из CSR не дают дополнительных полномочий.

Выпуск включается полем personal_ca_key_file в конфигурации менеджера. Это ключ центра сертификации, соответствующий ca; файл должен иметь права 0600/0400. По умолчанию выпуск отключён. Конфигурация загружается при запуске сервиса. Сам ключ не возвращается API и не включается в аудит. Для использования веб-выпуска менеджер должен иметь доступ к этому ключу; без него остаются доступны просмотр и отзыв ранее выпущенных сертификатов. В локальной конфигурации разработки выпуск включён существующим ключом локального CA.

Срок сертификата — 1–90 дней и не дольше срока CA. Ротация требует нового ключа: уже зарегистрированный в реестре публичный ключ повторно использовать нельзя. При первом управляемом выпуске используйте новый ключ, созданный командой CSR. Допускаются ECDSA P-256/P-384, Ed25519 и RSA от 3072 бит; встроенная команда создаёт P-256.

При ротации задаётся перекрытие от 0 до 24 часов. Новое значение может только сократить оставшийся срок допуска старых управляемых сертификатов, но не продлить его. При нуле старые сертификаты прекращают действовать немедленно. Отзыв также немедленно запрещает следующий запрос, в том числе через уже установленное TLS-соединение.

**Первый управляемый выпуск немедленно отключает прежние неуправляемые сертификаты этой учётной записи.** Перекрытие применяется только к сертификатам, уже учтённым менеджером. Предусмотрите административный доступ для установки первого нового сертификата. Bootstrap-доступ и сертификаты ролей admin/auditor не переводятся в этот реестр автоматически.

Реестр и версия ротации сохраняются в PostgreSQL. Ротация/отзыв выполняются транзакционно с проверкой version: конкурирующее изменение возвращает 409 и не отзывает текущий сертификат. Ошибка подписи, некорректный CSR или повторный ключ не изменяют допуск. Отключённая учётная запись не может получить новый сертификат и теряет доступ со всеми существующими сертификатами.

### Выпуск и замена через CLI

На компьютере пользователя:

```sh
bin/srk pki csr --key-out user-next.key --csr-out user-next.csr
```

Администратор получает только user-next.csr:

```sh
bin/srk --config admin.json manager certificates list alice
bin/srk --config admin.json manager certificates issue alice --csr user-next.csr --out user-next.crt --version 0 --days 30 --overlap-hours 1
```

Используйте текущую версию из list; 0 подходит для первого выпуска. Укажите новые имена файлов: CLI не перезаписывает существующие ключи и сертификаты. Пользователь устанавливает возвращённый сертификат вместе с соответствующим новым ключом; в его конфигурации сохраняются role=user, id=alice, installation, ca и HTTPS URL менеджера. Команда manager me позволяет проверить новый вход до истечения перекрытия.

Если ответ выдачи потерян, повторно скачайте уже выпущенный публичный сертификат, а не повторяйте ротацию с тем же ключом:

```sh
bin/srk --config admin.json manager certificates list alice
bin/srk --config admin.json manager certificates get alice --serial SERIAL --out recovered.crt
bin/srk --config admin.json manager certificates revoke alice --serial SERIAL --version CURRENT_VERSION
```

В интерфейсе доступны те же действия: вставка CSR, срок и перекрытие, скачивание сертификата, немедленный отзыв. При потере ответа обновите список и скачайте запись по отпечатку нового ключа/серийному номеру. Закрытый ключ сервер восстановить не может.

События аудита: certificate.rotate.requested, certificate.rotated, certificate.revoke.requested, certificate.revoked. Журнал содержит пользователя/исполнителя и серийный номер, без закрытых ключей. Автоматическое продление по таймеру, ротация CA и сертификатов сервисных компонентов в этот этап не входят.
