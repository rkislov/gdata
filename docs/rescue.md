# Аварийный диск SRK Rescue (0.6)

В версии 0.6 добавлена [прямая резервная копия физического диска из аварийной среды](rescue-capture-v06.md): отдельный код записи, передача в медиасервер, дедупликация, прогресс и журнал. Описанный ниже способ с заранее подготовленным RAW-файлом также сохраняется.

Автор: Кислов Роман Сергеевич. Исходники SRK — Apache-2.0. Linux, Alpine, GRUB и остальные пакеты образа сохраняют собственные лицензии. Образ создаётся и хранится локально; публикация не выполняется.

## Готовый образ и сборка

`make rescue-iso` собирает статический Go-клиент и ISO x86_64 в `.local/rescue/srk-rescue-amd64.iso`; рядом находятся SHA-256 и перечень пакетов. Нужны Go, Docker, интернет при сборке. Работа аварийной системы не требует доступа в интернет, но требует сетевого доступа к менеджеру и действующих копий на медиасервере. Конфигурации, пароли, ключи PKI и резервные копии в ISO не включаются (`.dockerignore` исключает их из контекста сборки).

По умолчанию меню открывается на локальном экране с клавиатурой. Второй пункт GRUB (клавиша `s`) включает последовательную консоль 115200 baud. ISO содержит BIOS и UEFI загрузчики, ядро Alpine linux-lts, модули хранения и Ethernet, DHCP, iproute2, lsblk и утилиты файловых систем. Система работает из RAM, диски автоматически не монтируются. Secure Boot, Wi-Fi, дополнительная прошивка сетевых карт и сертификация оборудования пока не реализованы. Рекомендуется не менее 2 ГиБ RAM; фактическое требование зависит от оборудования. Для конкретных RAID/NIC необходимо проверить наличие драйвера и прошивки в тестовой загрузке.

Запишите ISO на выделенный USB-носитель подходящей программой записи образов либо подключите как виртуальный CD через консоль сервера. Запись образа стирает USB-носитель. SRK не записывает его на подключённые к рабочему компьютеру диски автоматически.

Основа загрузчика: [официальное руководство grub-mkrescue](https://www.gnu.org/software/grub/manual/grub/html_node/Invoking-grub_002dmkrescue.html). Дистрибутив: [Alpine Linux](https://www.alpinelinux.org/downloads/). Версии реально включённых пакетов фиксируются рядом с ISO; побитовая воспроизводимость сборки не заявлена.

## Подготовка копии физического компьютера

Восстановление всего диска требует полного RAW-образа, включающего таблицу разделов, загрузочные области и файловые системы. Обычная файловая копия не является образом операционной системы.

1. Получите RAW-образ выключенного исходного компьютера либо согласованного снимка его диска. Получение снимков работающего физического диска в 0.5 не реализовано. Не создавайте образ чтением диска, на который продолжается запись.
2. Поместите **единственный** файл `system.img` в отдельный каталог внутри `allowed_roots` агента. Файл должен быть обычным, не устройством и не ссылкой; размер кратен 512 байтам. Не изменяйте его во время задания.
3. Создайте задание типа `disk-image`, режим `full`, источник — этот каталог. Агент использует существующую дедупликацию, проверяет неизменность размера и mtime, медиасервер проверяет блоки. Согласованность образа заявляет оператор; SRK не определяет, была ли исходная ОС выключена.
4. Успешная копия имеет `consistency=offline-disk-image`. Для неё доступно аварийное восстановление непосредственно на диск. Обычная функция восстановления через агент также может выгрузить `.img` в новый каталог.

Многодисковые системы восстанавливаются отдельными образами. Автоматическое изменение размеров разделов, восстановление на меньший диск, преобразование BIOS/UEFI и перенос на другой контроллер не выполняются.

## Подключение по одноразовому коду

В подробностях успешной резервной копии нажмите «Аварийный диск · код». Через CLI:

```
bin/srk --config .local/admin.json manager rescue issue BACKUP_RUN_ID
bin/srk --config .local/admin.json manager rescue revoke ACCESS_ID
```

Код `SRK1.…` содержит HTTPS URL менеджера, SHA-256 его конечного сертификата и случайный 256-битный секрет. Это конфиденциальный код доступа; передавайте его доверенным способом. Менеджер должен иметь доступный из аварийной сети `url`, а сертификат — соответствующее DNS-имя/IP. Локальный адрес `https://localhost:8443` с физического сервера указывает на сам сервер и для этого сценария не подходит.

Код срабатывает один раз за 10 минут; транзакция PostgreSQL атомарно удаляет его и выдаёт сессию только для выбранных копий. В каталоге хранятся хеши секретов, а не сами коды/токены. Сессия завершается через 4 часа с момента выпуска доступа. Повторное подключение требует нового кода. Отзыв ID удаляет код и связанную сессию. Выход из аварийного клиента отзывает сессию на сервере.

TLS 1.3: клиент проверяет точный отпечаток сертификата из кода, имя узла, срок и назначение сертификата; перенаправления запрещены. Поэтому в ISO не нужны закрытый ключ агента или CA, и код не передаётся серверу до проверки его подлинности. После замены сертификата нужен новый код. Перед подключением проверьте часы аварийной системы.

Менеджер проксирует только разрешённые манифесты и их блоки по mTLS с медиасервером. Сертификат менеджера получает только read-capability; write-capability этим путём запрещена. При первом чтении создаётся защита копии от GC до конца сессии; после отзыва она консервативно остаётся до истечения четырёх часов. Получение манифеста требует проверки целостности копии. Просроченную копию сначала нужно восстановить в каталоге/продлить хранение обычным административным механизмом.

## Аварийное меню и запись

Меню: Network (DHCP/статический IPv4), Connect, Find backups and restore RAW disk, Disconnect, Diagnostics shell, Reboot. После подключения выводятся только разрешённые копии. Меню текстовое; названия пунктов ASCII для совместимости с консолью сервера.

Предлагаются только достаточно большие диски с логическим сектором 512 байт. Исключаются USB, съёмные, смонтированные, read-only диски, swap, установочный ISO и устройства с активными RAID/device-mapper зависимостями. 4Kn и USB как целевой диск пока не поддерживаются. Диагностическая оболочка предназначена для опытного оператора и имеет root-права.

Оператор видит путь, модель, серийный номер и размер. Для записи нужно вручную набрать `ERASE /dev/… SERIAL`. Затем состояние проверяется повторно, устройство открывается эксклюзивно без следования симлинкам, сверяется его идентичность. Все прежние разделы целевого диска будут перезаписаны. Каждая скачанная порция сверяется с SHA-256 до записи, после fsync весь восстановленный диапазон перечитывается и проверяется повторно.

Увеличенный целевой диск не переразмечается; для GPT может потребоваться перенос резервного заголовка GPT штатной утилитой после проверки. Хвост большего диска не обнуляется. При обрыве восстановление начинается заново, а диск считается частично перезаписанным. Автоматической перезагрузки после записи нет.

Подключения, выпуск и отзыв доступа, чтение копий записываются в аудит. Сообщения начала/результата записи помечены `rescue.client_restore`: их сообщает клиент, это не независимое серверное доказательство успешной записи на физический диск.

## API

- Администратор: `POST /v1/rescue/codes {run_ids:[…]}`, `DELETE /v1/rescue/codes/{id}`.
- Одноразовый bootstrap: `POST /v1/rescue/pair {code:secret}`.
- Bearer-сессия аварийного клиента: `GET /v1/rescue/backups`, `GET /v1/rescue/backups/{run_id}`, `GET /v1/rescue/backups/{run_id}/chunks/{sha256}`.
- События: `POST /v1/rescue/events {run_id,status:started|verified|failed}`; выход `POST /v1/rescue/disconnect`.

Все остальные административные API этому токену недоступны. API ничего не форматирует и не записывает на диски менеджера/медиасервера.
