# Руководство администратора GData SRK 0.9.2

## Архитектура и требования

Менеджер хранит каталог и очередь в PostgreSQL, обслуживает веб-интерфейс
и координирует операции. Медиасервер хранит блоки и манифесты. Агент читает
источники и восстанавливает данные. Прокси выполняет интеграции виртуализации.
Один бинарник `srk` запускает все роли; для каждой нужен отдельный JSON и
сертификат с ролью и ID. Межкомпонентный обмен использует mTLS/TLS 1.3.

Для ALT Linux 10 (p10) подготовлен RPM x86_64 со статическим бинарником и
встроенным CSS. Go и Node.js на целевой машине не нужны. PostgreSQL
устанавливается и настраивается отдельно; профили баз данных, ВМ, Kubernetes
и устройств могут требовать дополнительных утилит и инфраструктуры.
Размер дисков планируйте по объёму, изменениям, удержанию и проверкам;
по умолчанию медиасервер сохраняет резерв свободного места 1 ГиБ.

## Установка ALT Linux 10

Скачайте RPM и `SHA256SUMS` из Releases репозитория. Проверяйте сумму
выбранного файла из каталога загрузки (SHA256 не заменяет проверку источника).
От root:

```sh
sha256sum --ignore-missing -c SHA256SUMS
apt-get update
apt-get install ./gdata-srk-0.9.2-alt1.x86_64.rpm
srk version
```

RPM создаёт системного пользователя `srk`, каталоги `/etc/srk`,
`/var/lib/srk`, `/var/log/srk`, устанавливает `/usr/bin/srk` и
`srk@.service`. Службы не запускаются до подготовки конфигурации.
Архив `gdata-srk-0.9.2-alt10-x86_64.tar.gz` содержит тот же бинарник,
unit и документацию; при ручной установке пользователя и каталоги создайте
самостоятельно. Не смешивайте ручную установку и RPM.

## Подготовка рабочей инсталляции

1. Назначьте постоянные DNS-имена, ID установки и компонентов, HTTPS-порты.
   Синхронизируйте время. Разрешите в межсетевом экране только нужные связи:
   браузер/CLI к менеджеру, компоненты к менеджеру и используемые пути данных
   агент/прокси/медиасервер; PostgreSQL доступен менеджеру.
2. Создайте отдельную PostgreSQL-базу и роль с правами на её схему. Настройте
   TLS и доверие к CA PostgreSQL. В `database_url` требуется
   `sslmode=verify-full`, корректное DNS-имя и доверенный корневой сертификат.
   Менеджер создаёт структуру каталога при запуске; сделайте резервную копию
   существующей БД перед обновлением.
3. На защищённом административном узле создайте CA и сертификаты. Пример
   ниже использует вымышленные DNS-имена, которые нужно заменить:

```sh
umask 077
srk pki init --dir /secure/srk-pki --installation production
srk pki issue --dir /secure/srk-pki --installation production \
  --role manager --id manager-01 --hosts manager.example.org
srk pki issue --dir /secure/srk-pki --installation production \
  --role media --id media-01 --hosts media.example.org
srk pki issue --dir /secure/srk-pki --installation production \
  --role agent --id agent-01 --hosts agent.example.org
srk pki issue --dir /secure/srk-pki --installation production \
  --role admin --id administrator
```

Сертификаты и ключи называются `<ID>.crt` и `<ID>.key`. На каждый узел
перенесите только его ключ/сертификат, публичный `ca.crt` и актуальный файл
отзыва `revoked.json` (первоначально `[]`). CA-ключ храните отдельно.
Административный сертификат не устанавливайте на рабочие агенты.

Создайте случайный bootstrap-пароль и общий для менеджера/медиасервера
секрет capabilities, например `openssl rand -hex 24 > admin.password` и
`openssl rand 48 > capability.key` при `umask 077`. Перенесите их по защищённому
каналу. Секрет capabilities нужен только соответствующим ролям.

4. Подготовьте `/etc/srk/manager.json` по примеру, заменив адреса, пароль БД
   (URL-encoded) и пути. Файл содержит секрет подключения: права 0600, владелец
   `srk`. Все закрытые ключи, пароль и capabilities — также 0600/0400.

```json
{
  "role": "manager",
  "id": "manager-01",
  "installation": "production",
  "listen": "0.0.0.0:8443",
  "url": "https://manager.example.org:8443",
  "ca": "/etc/srk/ca.crt",
  "cert": "/etc/srk/manager-01.crt",
  "key": "/etc/srk/manager-01.key",
  "revoked_file": "/etc/srk/revoked.json",
  "database_url": "postgres://srk:REPLACE@db.example.org/srk?sslmode=verify-full&sslrootcert=/etc/srk/postgres-ca.crt",
  "password_file": "/etc/srk/admin.password",
  "capability_key_file": "/etc/srk/capability.key",
  "max_parallel": 4,
  "per_agent": 1,
  "per_media": 4
}
```

Для `media.json` укажите роль/ID и его сертификат, `listen`, `url`,
`manager_url`, CA и список отзыва, `repository: /var/lib/srk/repository`,
`capability_key_file`; удалите параметры БД и bootstrap-пароля.
Для `agent.json` укажите его роль/ID/адреса/сертификат, `manager_url`,
`allowed_roots` (источники) и `restore_roots` (новые каталоги восстановления);
параметры репозитория и capabilities не нужны. Для `proxy.json` аналогично
задайте роль `proxy` и подготовленные профили интеграций.
`installation` должен совпадать у всех компонентов.

5. Создайте каталоги данных с владельцем `srk`. Дайте сервисному пользователю
   чтение источников и запись в корни восстановления с минимальными правами.
   Шаблон unit запрещает доступ к `/home` и запись вне `/var/lib/srk`,
   `/var/log/srk`. Для иных путей создайте обоснованный drop-in командой
   `systemctl edit srk@agent`, например `[Service]` и
   `ReadWritePaths=/srv/restore`; проверьте также права каталогов и
   `ProtectHome`. Не запускайте все службы от root ради обхода ограничений.

## Проверка и запуск

Для каждой установленной роли (пример менеджера):

```sh
runuser -u srk -- srk --config /etc/srk/manager.json manager check-config
systemctl enable --now srk@manager
systemctl status srk@manager
journalctl -u srk@manager -n 100 --no-pager
```

`check-config` проверяет локальную конфигурацию и сертификат; доступность
PostgreSQL и инфраструктуры подтвердите запуском и операциями.
Аналогично запустите `srk@media`, `srk@agent`, при необходимости `srk@proxy`.
Настройте клиентский JSON администратора с ролью `admin`, его ID, installation,
CA/ключом/сертификатом и `url` менеджера. Проверьте `manager nodes` через CLI.
В браузере доверьтесь CA и откройте HTTPS-адрес менеджера. Bootstrap-вход
использует пустой логин или `bootstrap` и пароль из `password_file`.

Создайте персонального администратора, операторов и аудиторов через
«Пользователи». Оператору выдайте явные разрешения, области заданий и площадок,
утверждённые цели восстановления. Пустая область означает отсутствие доступа.
Для персонального CLI используйте сертификат роли `user`, ID = username.
Подробнее: [права](access-control.md),
[цели восстановления и ротация сертификатов](recovery-access-and-certificates.md).

## Задания и приёмка

Создайте задание в интерфейсе или JSON через `manager jobs create --file`:

```json
{
  "name": "Документы",
  "agent_id": "agent-01",
  "media_id": "media-01",
  "source": "/srv/documents",
  "mode": "incremental",
  "interval_seconds": 86400,
  "retention_days": 30,
  "enabled": true
}
```

Запустите копирование, проверку и восстановление в отдельный каталог по
[руководству пользователя](user-guide.md). Сверьте файлы, права и работу
приложения. Включайте расписания после успешной проверки. Зафиксируйте RPO/RTO,
ёмкость, сроки хранения и результат восстановления. Для PostgreSQL, ВМ,
Kubernetes и устройств выполните отдельную приёмку по профильным инструкциям.

## Эксплуатация и восстановление

Ежедневно проверяйте ошибки очереди, доступность компонентов, свободное место,
возраст последней успешной копии и карточки 3-2-1. Проверяйте сроки сертификатов,
репликацию и WAL; регулярно проводите пробное восстановление.
Очистку выполняйте только штатным preview/plan и подтверждением по
[инструкции жизненного цикла](lifecycle.md). Не удаляйте блоки вручную.

Настройте зашифрованное резервирование каталога менеджера, ключ шифрования
храните отдельно от архивов. Сохраните копию вне исходного сервера и проверяйте
её восстановлением в отдельную БД. Полная процедура, команды, репликация и
снятие блокировки после аварии:
[резервирование и аварийное восстановление каталога](catalog-disaster-recovery.md).
Сохраняйте также независимые копии репозиториев, PKI и настроек: один архив
каталога не содержит пользовательские резервные данные.

Перед обновлением сохраните каталог, конфигурации и ключи, проверьте новый
пакет на стенде. Остановите соответствующие экземпляры systemd, установите
RPM через `apt-get install ./...rpm`, проверьте конфигурации и запустите службы.
После запуска выполните резервирование и пробное восстановление. Откат БД
выполняйте из проверенной копии: замена бинарника не откатывает схему.
Удаление пакета не удаляет автоматически данные и секреты; их утилизация
выполняется отдельно по установленной политике хранения.

## Сборка и GitHub

```sh
make test
make altlinux
```

Нужны Go 1.26+, Docker и доступ к образу ALT p10/репозиториям пакетов.
Результат в `dist/`: RPM x86_64, tar.gz и SHA256SUMS. Бинарник собирается
без CGO; RPM упаковывается в официальном контейнере ALT p10. CI повторяет
сборку, установку RPM и проверку конфигураций в чистом контейнере.
Эта проверка не заменяет испытания полного развёртывания с systemd,
PostgreSQL, реальными источниками и оборудованием на ALT Linux 10.

Публичный репозиторий: https://github.com/rkislov/gdata. Право записи имеет
владелец `rkislov`; не добавляйте других collaborators с записью или deploy
keys с write-доступом, если требуется сохранить этот режим. Публикация изменений
от остальных — через fork и PR; сообщения — через Issues. Слияние и публикация
релизов выполняются владельцем. Apache-2.0 разрешает изменять собственные копии.
