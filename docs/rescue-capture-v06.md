# SRK 0.6: резервная копия физического диска из аварийной среды

Автор: Кислов Роман Сергеевич. Код SRK распространяется под Apache-2.0; компоненты Linux/Alpine/GRUB сохраняют свои лицензии. Публикация проекта не выполняется.

## Что реализовано

SRK Rescue читает весь выбранный физический диск и передаёт блоки непосредственно на медиасервер. Промежуточный RAW-файл в RAM или на другом диске не создаётся. Сохраняются все адресуемые секторы: MBR/GPT, резервная GPT, загрузочные области, EFI-разделы, файловые системы, их внутренние права/ACL и неиспользуемое пространство. Результат — полная RAW-копия; сжатие и копирование только занятых блоков файловой системы не выполняются.

Программный лимит размера — 4 TiB; нагрузочные испытания на таком объёме ещё не выполнялись. Принимаются диски с логическим сектором 512 или 4096 байт. Формат исходного диска не преобразуется. Восстановление требует диск не меньшего размера с тем же логическим сектором. Для старых RAW-копий без метаданных геометрии используется сектор 512 байт. Работа с несколькими дисками выполняется отдельными заданиями.

Исходный диск должен быть отключён от работающей ОС, не смонтирован и не занят swap, RAID или device-mapper. Для общего SAN/LUN необходимо остановить запись и с других узлов. Горячий захват работающего физического диска в этой версии не реализован. Аварийная система загружается в RAM; системные диски автоматически не монтируются.

## Настройка медиасервера

В конфигурации выбранного медиасервера включите:

```json
{
  "rescue_capture_enabled": true,
  "manager_url": "https://manager.example:8443"
}
```

Остальные поля существующей конфигурации сохраняются. Перезапустите медиасервер. После heartbeat он появится в списке доступных для SRK Rescue. На локальном стенде режим уже включён в `.local/media.json`.

Режим выключен по умолчанию. При включении TLS медиасервера допускает подключение без клиентского сертификата; доступ к обычным служебным API по-прежнему требует mTLS. Доступ без сертификата предоставляют только специальные capture-endpoints и только с подписанным ограниченным разрешением. Если режим выключен, медиасервер требует клиентский сертификат уже при TLS-handshake.

Менеджер и медиасервер должны иметь адреса, доступные из аварийной сети, и сертификаты с соответствующими DNS/IP SAN. Менеджер использует адрес медиасервера из зарегистрированного узла. Локальный `localhost` на физической машине указывает на неё саму: для реального развёртывания замените loopback-адреса публичными адресами внутренней сети, настройте `listen`, `url` и сертификаты. Закрытый ключ CA в ISO не включается.

## Создание копии

1. Соберите ISO: `make rescue-iso`. Файл — `.local/rescue/srk-rescue-amd64.iso`; рядом SHA-256 и перечень пакетов.
2. В веб-интерфейсе нажмите **«Диск · SRK Rescue»**. Задайте название, медиасервер, срок хранения и максимальный размер диска. Выпустите отдельный код записи.
3. Загрузите физический компьютер с ISO. Выберите локальный экран либо serial-console, настройте сеть, пункт **Connect using one-time code**.
4. Выберите **Back up a physical disk to media server**. Меню покажет доступные диски, размер, сектор, модель и серийный номер, если устройство их сообщает. Для mdev-среды идентификаторы дополнительно читаются из sysfs.
5. Выберите исходный диск и введите `BACKUP /dev/… SERIAL`. Диск открывается только на чтение, эксклюзивно, без следования симлинкам. Перед открытием повторно проверяются состояние и идентичность. USB/съёмные носители и загрузочный ISO исключаются; read-only исходный диск допустим.
6. Следите за заданием в разделе **«Активность»**. В подробностях доступны геометрия, процент передачи, дедупликация и журнал операции.
7. После проверки всех блоков медиасервером задание получает статус «Успешно». В карточке можно выпустить отдельный код восстановления и восстановить копию обычным аварийным меню.

Команда CLI для выпуска кода:

```
srk --config admin.json manager rescue issue-backup \
  --media media-01 --name "АРМ-01 · системный диск" \
  --retention-days 30 --max-bytes 549755813888

srk --config admin.json manager runs get RUN_ID
srk --config admin.json manager audit
srk --config admin.json --endpoint https://media.example:8444 media captures get RUN_ID
srk --config admin.json manager rescue revoke ACCESS_ID
```

Код подключения срабатывает один раз за 10 минут. Сессия записи действует до 12 часов с момента выпуска доступа; она разрешает ровно одно задание на выбранном медиасервере и ограничивает размер. Код восстановления прав записи не имеет; код записи не получает права чтения существующих копий. Коды и токены не сохраняются в ISO или журнале. Для повторного нового задания нужен новый код.

## Дедупликация, подтверждения и целостность

Клиент читает блоки по 4 MiB, вычисляет SHA-256 и запрашивает наличие блока в контексте конкретного задания. Медиасервер проверяет существующий блок и размер; известные блоки повторно не передаются. Отсутствующий блок передаётся напрямую по HTTPS, проверяется по размеру и SHA-256 и сохраняется штатным репозиторием. Общий менеджер не проксирует содержимое диска.

После сохранения данных медиасервер fsync-ит фиксированную запись журнала подтверждений. Запись связывает индекс, размер, количество переданных байтов и SHA-256. Повтор того же блока идемпотентен, другой хеш для подтверждённого индекса отвергается. Пропустить индекс нельзя. Во время передачи действует write lease, защищающая блоки от GC.

После передачи клиент запрашивает завершение. Медиасервер сам строит манифест по своему журналу — список блоков и результат проверки не принимаются со слов клиента. Проверяется полная последовательность, размеры и SHA-256 всех сохранённых блоков. Манифест фиксируется атомарно. Процент до этого ограничен 99%; во время полной проверки показывается отдельный этап без выдуманного процента. 100% и успешный статус появляются только после подтверждения медиасервера менеджером.

Полная проверка больших дисков может занять значительное время. Heartbeat медиасервера отправляется независимо от тяжёлого подсчёта статистики репозитория; статистика места может быть старше heartbeat. Срок хранения отсчитывается от начала задания, как в манифесте.

Сетевой клиент использует TLS 1.3 и проверяет точные отпечатки конечных сертификатов менеджера и медиасервера. Отпечаток медиасервера получен менеджером по проверенному mTLS-соединению. Перенаправления запрещены. Перед каждым прямым запросом медиасервер проверяет по mTLS у менеджера, что задание, сессия и разрешение активны; при недоступном менеджере новая запись не разрешается. Требуется корректное время компонентов.

## Очередь, журнал и ошибки

Capture-задания используют общие лимиты менеджера и лимиты медиасервера. До получения слота клиент ожидает в очереди. После выбора диска появляется обычная запись `Run(kind=backup)`; в ней сохранены метаданные диска. Процент и объёмы поступают от медиасервера, а не из произвольных сообщений клиента. CSV/XLSX включают эти задания, итоговые объёмы и статус проверки.

Аудит содержит выпуск кода, подключение, постановку в очередь, готовность медиасервера, изменения этапа и каждые примерно 5% подтверждённого прогресса, результат и запрос отмены. В подробностях задания показываются последние 200 его событий, хранящихся в PostgreSQL. Перезапуск браузера не теряет журнал. По каждому блоку ведётся отдельный долговечный журнал на медиасервере; миллион SQL-событий на большой диск не создаётся.

Отмена из интерфейса и отзыв доступа прекращают выдачу разрешений на новые запросы. Уже принятые данные не стираются автоматически. Частичная копия не объявляется успешной; её блоки консервативно защищены до истечения write lease. После этого неиспользуемые блоки может убрать обычный GC. Завершённый физический манифест, результат которого менеджер не подтвердил из-за сбоя/отмены, следует проверить через инвентаризацию и явный импорт.

При коротком сетевом сбое запрос блока повторяется ограниченное число раз. Журнал восстанавливает подтверждённый префикс после перезапуска медиасервера и отбрасывает только неполную последнюю запись, на которую подтверждение не могло быть выдано. Повреждённая полная запись не игнорируется. Автоматическое возобновление после перезагрузки самого SRK Rescue или менеджера не реализовано: менеджер помечает незавершённое задание ошибкой. Новое задание перечитывает диск, используя уже сохранённые блоки через дедупликацию. Отсутствие передачи 15 минут считается ошибкой; сессия также ограничена 12 часами.

## API 0.6

Менеджер:

- `POST /v1/rescue/codes` с `operation=backup`, `name`, `media_id`, `retention_days`, `max_bytes` — административное разрешение.
- `POST /v1/rescue/captures` — выбор геометрии через write-сессию.
- `GET /v1/rescue/captures/{id}` — состояние и ограниченное разрешение прямой загрузки.
- `POST /v1/rescue/captures/{id}/abort` — запрос остановки владельцем сессии.
- `GET /v1/rescue/captures/{id}/authorize` — только mTLS-сертификат выбранного медиасервера.
- `GET /v1/runs/{id}/events` — авторизованное чтение событий задания.

Медиасервер при включённом capture-режиме:

- `POST /v1/captures/{id}` — только менеджер, регистрация неизменяемого задания.
- `GET /v1/captures/{id}` — статус; mTLS-администратор/аудитор/менеджер либо ограниченное разрешение задания.
- `POST /v1/captures/{id}/blocks/{index}/{hash}` — проверка наличия и подтверждение существующего блока.
- `PUT /v1/captures/{id}/blocks/{index}/{hash}` — загрузка отсутствующего блока, не более 4 MiB.
- `POST /v1/captures/{id}/commit` — начать полную проверку; ответ 202, затем опрос состояния.

Обычные `/v1/chunks`, `/v1/snapshots` и административные API capture-токену недоступны.

## Проверка и ограничения оборудования

Реальные диски рабочей машины при разработке не подключались. Автоматические тесты проверяют полный HTTPS/mTLS цикл, границы прав, размер, отзыв, прогресс, журнал, дедупликацию, повтор блока, неполную запись журнала, перезапуск хранилища и отказ при повреждении данных.

Проверка в QEMU использует только два файла как виртуальные диски: исходный read-only диск 64 MiB с GPT и тестовым BIOS-загрузчиком и пустой целевой диск. ISO создал резервную копию напрямую, затем восстановил её на второй диск. SHA-256 исходного и восстановленного дисков совпали, исходный файл не изменился. При этой проверке передано 8 MiB, 56 MiB повторно использованы. Отдельно проверяется исполнение тестового загрузчика с восстановленного диска. Это проверка сохранения и загрузки тестового boot sector, а не сертификация конкретной ОС.

Для повторения локального стендового теста на macOS/Docker Desktop:

```
make build
make rescue-iso
python3 scripts/test-rescue-disk.py
```

Сервисы и PostgreSQL должны быть запущены. Тест создаёт одну копию тестового диска в локальном каталоге, а временные виртуальные диски — только в `.work/v06-e2e`. Внешние адреса и физические устройства тест не использует. Host-side HTTP-клиент теста допускает локальный dev-сертификат; настоящий аварийный клиент проверяет отпечатки сертификатов. Тестовые коды скрываются и редактируются из сохранённого лога.

BIOS/UEFI загрузка самого ISO поддерживается. Secure Boot, автоматическое изменение размеров разделов, преобразование BIOS/UEFI, установка драйверов в восстановленную ОС и дополнительная vendor firmware остаются вне этой версии. На реальном сервере нужно отдельно проверить контроллер, сетевую карту и успешную загрузку восстановленной ОС.
