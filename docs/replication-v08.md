# Репликация между медиасерверами — версия 0.8

Copyright 2026 Кислов Роман Сергеевич. Apache-2.0.

Репликация переносит выбранную пригодную копию в отдельный репозиторий второго медиасервера этой же инсталляции. Поддерживаются манифесты файлов, физических дисков, ВМ, S3, MySQL/MariaDB и базовых копий PostgreSQL. После проверки появляется самостоятельная точка восстановления: её можно проверить, восстановить, реплицировать дальше и обслуживать обычными средствами хранения.

## Запуск

В подробностях успешного бэкапа нажмите **Реплицировать**, выберите другой подключённый медиасервер и срок хранения 1–36500 дней. В активности появляется отдельная операция «Репликация»: источник и приёмник, процент текущего этапа передачи, новые блоки/дедупликация и журнал. После успеха кнопка «Открыть копию на приёмнике» ведёт к новой точке восстановления.

CLI:

```sh
srk --config /etc/srk/admin.json --wait --timeout 12h manager runs replicate SOURCE_RUN_ID --media TARGET_MEDIA_ID --retention-days 90
srk --config /etc/srk/admin.json manager runs get OPERATION_ID
srk --config /etc/srk/admin.json manager runs cancel OPERATION_ID
```

API управления:

```http
POST /v1/runs/SOURCE_RUN_ID/replicate
Idempotency-Key: unique-request-key
Content-Type: application/json

{"target_media_id":"media-offsite","retention_days":90}
```

Возвращается 202 и операция с `kind=replicate`, `replication` и будущим `copy_run_id`. Повтор идентичного запроса с тем же ключом возвращает ту же операцию; другие параметры с тем же ключом дают 409. Вызов требует администратора: сертификат либо веб-сессия с проверкой Origin. Аудитор может читать состояние и журнал.

## Передача и проверка

Система управления ставит операцию в общую очередь и выдаёт приёмнику краткосрочное разрешение чтения конкретной точки источника. Данные идут **напрямую media → media**; система управления получает только состояние и квитанцию результата. Оба медиасервера должны работать на версии 0.8 или новее. Требуются сетевой доступ приёмника к HTTPS-адресу источника, сертификаты одной инсталляции, доверенный CA и одинаковый ключ capabilities. Сертификаты сверяются по роли и ID; перенаправления запрещены. Саморепликация и репозитории с одинаковым repository_id отклоняются. Скопированный вручную каталог с тем же ID не считается независимым репозиторием.

Проверяются точные байты манифеста и его контрольная сумма, SHA-256 и длина каждого блока источника, существующие блоки приёмника и полный набор файлов при атомарной фиксации. Все исходные уникальные блоки перечитываются даже при наличии на приёмнике: хорошая целевая копия не должна скрывать повреждение источника. Дедупликация экономит запись и место на приёмнике; в этой версии повторная проверочная передача всё ещё читает блоки по сети. Чужие точки/блоки за пределами разрешения недоступны.

Во время чтения источник защищён read lease; приёмник держит write lease, чтобы GC не удалил блоки незавершённой операции. Срок разрешений ограничен 12 часами. Общий MaxParallel и PerMedia учитывают оба медиасервера; агент исходной ОС в передаче не участвует и его слот не занят.

Манифест приёмника получает новый ID, новый JobID, `mode=full` и пустой Base. Инкрементальная точка содержит полный список файлов и становится самостоятельной без цепочки исходного репозитория. Проверенная квитанция сохраняется в целевом манифесте; регистрация точки восстановления и успешного статуса операции выполняется одной транзакцией каталога.

## Независимое хранение

Срок хранения начинается после передачи и проверки. Изменение срока или hold источника, его последующее удаление и GC не изменяют реплику. Реплика имеет собственные политику хранения и hold; изменение политики приёмника не распространяется обратно на источник. Автоматическая очистка и ручные операции применяются к каждому репозиторию отдельно. Квитанция содержит происхождение, дату исходных данных, хеш исходного манифеста и срок хранения на момент создания реплики.

Размещение второго сервера на другой площадке настраивает администратор. Само наличие двух медиасерверов не доказывает off-site хранение или выполнение всех условий 3-2-1.

## Отмена и сбои

До фиксации манифеста отмена/ошибка не создаёт пригодную точку. Проверенные частичные блоки остаются для дедупликации при новой попытке и безопасно убираются обычным GC после закрытия leases. Повреждённый существующий блок не переписывается молча: операция завершается ошибкой для диагностики хранилища.

При потере подтверждения или перезапуске управления целевой манифест мог успеть зафиксироваться. В подробностях ошибочной/отменённой репликации используйте **Проверить завершённую копию на приёмнике**. СРК сверяет квитанцию, повторно проверяет все целевые блоки и регистрирует точку без чтения исходника. CLI:

```sh
srk --config /etc/srk/admin.json manager runs reconcile-replication OPERATION_ID
```

Незавершённая передача автоматически после перезапуска не возобновляется. Кнопка «Повторить передачу» создаёт новую операцию и использует существующие проверенные блоки. Не повторяйте передачу вместо проверки квитанции, если есть вероятность уже завершённой копии и нужно избежать дубликата.

## PostgreSQL и границы версии

Начиная с 0.8.1, опция `include_wal: true` создаёт непрерывную политику WAL после базовой реплики. Для уже существующей удалённой базы политика включается отдельно. [Настройка WAL-репликации и удалённого PITR](wal-replication.md). Без этой опции базовая операция 0.8 по-прежнему переносит только файлы базы и включённые в них WAL. Межинсталляционный обмен, ограничение полосы сети и физические ленты — отдельные этапы.

## Проверки

Интеграционные тесты на реальных HTTPS/mTLS-сервисах СРК и отдельной тестовой PostgreSQL проверяют: передачу между репозиториями, независимый срок хранения, дедупликацию, восстановление ВМ после удаления исходных блоков, разворачивание инкрементального манифеста в самостоятельную копию, повреждения обеих сторон, отмену, GC leases, права и аудит, корректный процент передачи, идемпотентность и восстановление регистрации из устойчивой квитанции. Облачная ВМ в этом тесте обслуживается стендом API; гостевая ОС не запускается.
