# Резервирование каталога и восстановление менеджера СРК

## Состав и защита копии

Копия содержит согласованный логический снимок 12 таблиц каталога PostgreSQL: задания, операции, аудит, узлы, настройки защиты и целей восстановления, политики Kubernetes/WAL, пользователей с хешами паролей и правами, реестр персональных сертификатов и состояние аварийного восстановления. Все таблицы читаются в одной транзакции REPEATABLE READ. Изменения, завершившиеся после начала снимка, в него не попадают.

В зашифрованный комплект входят конфигурация менеджера, его сертификат и закрытый ключ, доверенный CA, bootstrap-пароль, ключ capabilities, файл отзыва сертификатов и ключ выпуска персональных сертификатов, если он настроен. Политика резервирования каталога сохраняется отдельным файлом catalog-policy.json. Пользовательские закрытые ключи, находящиеся на компьютерах пользователей, менеджер не получает и не сохраняет.

Формат .srkcat: сжатый поток записей с блочным шифрованием XChaCha20-Poly1305. Проверяются все блоки, завершающий маркер, gzip-контрольная сумма, состав таблиц, количество строк и совместимость схемы. Отдельно отображается SHA-256 зашифрованного файла. Незавершённый архив не публикуется как готовая копия. После создания автоматически выполняется полная проверка. Файлы архива и журналов имеют права 0600, каталог — 0700; второй процесс записи в то же хранилище блокируется.

Ключ восстановления — отдельный файл из 32 случайных байт. Он **не входит в архив** и не выдаётся через HTTP. Для восстановления после потери узла необходимо заранее вынести архив и ключ с узла менеджера, сохранив их раздельно. Локальная копия сама по себе не обеспечивает off-site. Архивы содержат административные секреты, поэтому доступ к расшифрованному комплекту равнозначен административному доступу к инсталляции.

## Настройка

Создайте ключ с помощью CLI; существующий файл не перезаписывается:

```sh
bin/srk catalog-recovery keygen --out /secure/srk-catalog.key
```

В конфигурации менеджера задайте абсолютные пути:

```json
{
  "catalog_backup": {
    "directory": "/srv/srk/catalog-backups",
    "key_file": "/secure/srk-catalog.key"
  }
}
```

Ключ должен находиться вне каталога архивов, иметь права 0600 или 0400. Перезапустите менеджер в штатном порядке. Без этой настройки каталог управления продолжает работать, но создание архивов отключено.

В локальном контуре разработки настроены `.local/catalog-backups` и `.local/catalog-recovery.key`, включён интервал 86400 секунд. Эти пути расположены на одном компьютере; внешнее хранение требуется организовать отдельно.

## Веб-интерфейс и CLI

Раздел «Каталог СРК» доступен только администратору. Он позволяет создать копию, задать интервал, посмотреть прогресс и журнал, повторно проверить и скачать зашифрованный архив. Интервал 0 отключает расписание; разрешён диапазон от 60 секунд до 30 суток. Одновременно выполняется одна копия каталога. При недоступности менеджера расписание не исполняется; после запуска просроченный запуск выполняется один раз. Неуспешная попытка не вызывает бесконечный цикл немедленных повторов.

```sh
bin/srk --config admin.json --json manager catalog-backups list
bin/srk --config admin.json --wait --timeout 10m manager catalog-backups create
bin/srk --config admin.json manager catalog-backups policy --version 0 --interval-seconds 86400
bin/srk --config admin.json manager catalog-backups verify ARCHIVE_ID
bin/srk --config admin.json manager catalog-backups download ARCHIVE_ID --out /safe/COPY.srkcat
```

Для изменения расписания используйте текущую version из list; устаревшая версия возвращает конфликт. Параметр --wait ожидает результат, но истечение клиентского тайм-аута не отменяет создание на менеджере. Журнал копий хранится рядом с архивами и остаётся доступным без исходной базы. После перезапуска прерванная копия помечается ошибкой. Сроки хранения, удалённая репликация и учебные восстановления управляются той же политикой; настройка приведена ниже.

Проверка скачанного файла не требует ни PostgreSQL, ни работающего менеджера:

```sh
bin/srk catalog-recovery verify --archive /safe/COPY.srkcat --key-file /secure/srk-catalog.key
```

Команда выводит только описание снимка и количество строк; конфигурация и секреты в stdout не выводятся.

## Аварийное восстановление

1. Остановите либо изолируйте прежний менеджер, исключив его возвращение в сеть. Блокировка PostgreSQL не позволяет восстановление при работающем менеджере в той же базе, но не может обнаружить прежний менеджер в другой базе или на изолированном узле.
2. Подготовьте PostgreSQL и отдельные реквизиты подключения для восстановленного менеджера. Сохраните URL в обычный файл с правами 0600/0400; не передавайте пароль в аргументах процесса. Для удалённой базы требуется sslmode=verify-full; sslmode=disable допустим только для loopback-разработки.
3. Используйте совместимую сборку СРК: формат проверяет версию и отпечаток определения схемы. Сначала восстановите на соответствующей версии, затем выполняйте штатное обновление.
4. Выберите новую, ещё не существующую схему и новый абсолютный каталог для восстановленных настроек. Родительский каталог должен существовать.

```sh
bin/srk catalog-recovery restore \
  --archive /safe/COPY.srkcat \
  --key-file /secure/srk-catalog.key \
  --database-url-file /secure/recovery-db.txt \
  --schema srk_recovered \
  --installation INSTALLATION_ID \
  --directory /srv/srk/recovered
```

Команда работает без исходного каталога и без исходной конфигурации менеджера. Она сверяет идентификатор инсталляции, получает блокировку управления, создаёт новую схему, загружает данные и полностью проверяет архив до фиксации транзакции. При повреждении, неправильном ключе или другой инсталляции новая схема откатывается. Существующие схемы и каталоги настроек не перезаписываются.

Результат содержит путь к manager.json. Все восстановленные секреты находятся в новом каталоге с правами 0600, сам каталог имеет права 0700. Реквизиты PostgreSQL заменяются на предоставленные новые, пути к ключам и сертификатам переписываются. Автоматическая очистка хранилищ и расписание резервирования самого каталога в восстановленной конфигурации отключены. Для последнего нужно заново подключить внешне сохранённый ключ и каталог архивов; исходная политика лежит в catalog-policy.json.

Если фиксация транзакции не подтверждена из-за потери связи, команда сохраняет каталог восстановленных материалов и сообщает об этом. Проверьте наличие схемы и состояние PostgreSQL; не считайте такой результат успешным и не удаляйте материалы до выяснения. Истёкший после даты копии сертификат менеджера потребуется обновить перед запуском; ключ CA включён только если он был настроен у менеджера для выпуска персональных сертификатов.

Запуск после проверки адресов, портов и сертификатов:

```sh
bin/srk --config /srv/srk/recovered/manager.json manager check-config
bin/srk --config /srv/srk/recovered/manager.json manager serve
```

## Режим проверки после восстановления

Сразу после восстановления:

- Все расписания заданий, репликации WAL и проверок Kubernetes выключены. Список ранее включённых политик сохранён в состоянии восстановления.
- Прежние queued/running операции помечены ошибкой с требованием сверки исполнителей; очередь не воспроизводится.
- Одноразовые коды и сессии SRK Rescue удалены. Веб-сессии не восстанавливаются.
- Время последнего наблюдения узлов сброшено; требуются новые heartbeat.
- Персональный вход и операционные изменения заблокированы. Системные административные сертификаты и bootstrap-вход позволяют проверить каталог, пользователей, сертификаты и снять блокировку.

Права, пароли и отзывы сертификатов соответствуют **моменту копии**. До подтверждения проверки администратор должен повторить отключения пользователей и отзывы сертификатов, выполненные после этой даты. При необходимости используйте восстановленный bootstrap.password для веб-входа с пустым логином или bootstrap. Личные ключи CLI-администраторов следует сохранять отдельно от менеджера.

После сверки старого узла, прав, реестра сертификатов, репозиториев и узлов подтвердите восстановление в разделе «Каталог СРК», введя идентификатор инсталляции. Альтернатива через CLI с административным сертификатом:

```sh
bin/srk --config admin.json manager catalog-backups acknowledge \
  --archive-id ARCHIVE_ID --confirm-installation INSTALLATION_ID
```

Подтверждение разрешает персональный вход и ручные операции, но не включает расписания автоматически. Включайте нужные задания и политики отдельно после проверки доступности копий и сверки прерванных операций на медиасерверах. События создания, скачивания, проверки и подтверждения восстановления записываются в аудит.

## Границы

Архив каталога не содержит блоки резервных копий медиасерверов, содержимое лент/flash, внешние backupstore Longhorn, конфигурации агентов и медиасерверов либо глобальные роли PostgreSQL. Они должны сохраняться отдельно. Новые данные после даты снимка и изменения отзывов сертификатов автоматически не реконструируются. Доступ к уже существующим резервным копиям требует исходных репозиториев и последующей сверки/импорта при необходимости. Автоматическое HA-переключение остаётся следующим этапом. Учебное восстановление проверяет импорт каталога и безопасное состояние после восстановления; оно не проверяет запуск веб-сервера, доступность рабочих хранилищ и восстановление данных приложений.


## Репликация и независимые сроки хранения

В разделе «Каталог СРК» укажите ID зарегистрированного медиасервера, локальный и удалённый сроки хранения. Новые завершённые архивы автоматически передаются по mTLS. На приёмнике сохраняется исходный зашифрованный файл; ключ расшифрования туда не передаётся. Приёмник проверяет SHA-256, сохраняет файл и выдаёт квитанцию с размером и сроком хранения. Повторная отправка того же архива сохраняет исходный срок; другой хеш под тем же ID отвергается. Повторная передача правильного архива позволяет исправить повреждённый файл на приёмнике.

Локальный срок отсчитывается от создания, удалённый — от получения. Изменение политики применяется к новым отправкам и не сокращает сроки уже полученных копий. `local_retention_days=0` означает бессрочное локальное хранение. Для удалённой копии нужен срок от 1 до 36500 дней. При настроенной автоматической репликации локальная очистка ждёт подтверждённую, ещё не просроченную удалённую квитанцию. Недоступный медиасервер не приводит к удалению неподтверждённого исходника. Удалённая очистка работает самостоятельно каждую минуту, даже при недоступном менеджере; текущая загрузка уже открытого файла завершается независимо от очистки.

```sh
bin/srk --config admin.json manager catalog-backups policy \
  --version CURRENT_VERSION --interval-seconds 86400 \
  --media media-remote --local-days 14 --remote-days 90 \
  --drill-interval-seconds 604800
bin/srk --config admin.json --wait --timeout 2h manager catalog-backups replicate ARCHIVE_ID --media media-remote
bin/srk --config admin.json manager catalog-backups remote-list media-remote
bin/srk --config admin.json manager catalog-backups remote-download ARCHIVE_ID --media media-remote --out /safe/REMOTE.srkcat
```

Команда `policy` заменяет всю политику; передавайте все нужные поля. Пустой `--media` отключает автоматическую отправку. Ручная отправка использует `--remote-days`, сохранённый в политике. Кнопка «Копии на указанном медиасервере» получает текущий инвентарь и позволяет скачать архив даже после истечения локального срока.

На медиасервере файлы находятся в `<repository>/catalog-copies/`: `.srkcat` и отдельные JSON-квитанции. Этот каталог не участвует в дедупликации пользовательских снимков; предел одного архива — 16 GiB. При полной утрате менеджера архив можно забрать из этого каталога средствами администратора медиасервера и использовать автономный `catalog-recovery verify/restore`. Ключ восстановления должен быть сохранён отдельно заранее. Все HTTP-операции менеджера доступны только администраторам; медиасервер принимает каталог только от роли manager своей инсталляции.

Размещение на другой физической площадке обеспечивает администратор: иной ID медиасервера сам по себе не доказывает off-site-размещение.

## Плановая проверка восстановления

Подготовьте отдельную PostgreSQL-базу с отдельной учётной записью и доступом только к этой базе. Сохраните URL подключения в файл 0600/0400 и задайте в `catalog_backup` конфигурации менеджера:

```json
{
  "directory": "/srv/srk/catalog-backups",
  "key_file": "/secure/catalog-recovery.key",
  "drill_database_url_file": "/secure/catalog-drill-db.txt"
}
```

Имя тестовой базы должно отличаться от имени рабочей, даже на другом сервере. Для удалённого PostgreSQL требуется `sslmode=verify-full`. Учётная запись должна иметь возможность создать схему и таблицы внутри тестовой БД. URL и пароль не принимаются через веб-интерфейс, не передаются в аргументах CLI и не выводятся в отчёты.

Проверка выполняет настоящий импорт во временную схему `srk_drill_<ID>` внутри транзакции, проверяет шифрование, схему, строки и ключевые материалы, применяет блокировку восстановления, останавливает восстановленные расписания/очереди и удаляет одноразовые Rescue-токены. После проверок транзакция откатывается вместе со схемой. Ни менеджер из копии, ни агенты не запускаются; подключения к рабочим хранилищам не выполняются. Расшифрованные настройки и ключи не записываются на диск. Временный зашифрованный файл удаляется; оставшийся после аварии процесса файл удаляется при следующем открытии хранилища. PostgreSQL откатывает незавершённую транзакцию при разрыве соединения.

```sh
bin/srk --config admin.json --wait --timeout 2h manager catalog-backups drill ARCHIVE_ID --media media-remote
# Локальная проверка без скачивания с медиасервера:
bin/srk --config admin.json --wait --timeout 2h manager catalog-backups drill ARCHIVE_ID
bin/srk --config admin.json --json manager catalog-backups list
```

Расписание проверяет последнюю подтверждённую ещё хранящуюся удалённую копию, если задан медиасервер; иначе последнюю локальную. Интервал — 0 (вручную) либо 60–2592000 секунд. Репликация и проверки выполняются последовательно, отдельно от создания очередной копии. Неудачная автоматическая отправка повторяется не чаще раза в минуту. Отчёт содержит источник, этапы, прогресс, даты, размер, квитанцию приёмника либо состав восстановленного каталога и подтверждение очистки. Он сохраняется в `operations.json`, а итог и инициатор — в аудите. Прерванная операция после перезапуска получает статус ошибки; её можно повторить. После аварийного восстановления менеджера автоматическое выполнение остаётся заблокировано до административной проверки.
