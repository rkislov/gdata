# Проверка версии 0.1

Дата: 28 октября 2026 года.

## Окружение

Go 1.25.0, macOS ARM64, PostgreSQL 16.15. Проверки HTTP используют настоящие TLS-соединения и сгенерированный для тестов CA. Интеграционные проверки используют отдельную базу `srk_test` с временными схемами, а не рабочий каталог локального стенда.

## Автоматические проверки

Команда `SRK_TEST_DATABASE_URL=... go test -race -count=1 -timeout 60s ./...` завершилась успешно: 23 теста верхнего уровня, включая пять интеграционных тестов управления с PostgreSQL. `go vet ./...` завершился без ошибок.

Проверены конфигурация и защита приватного ключа, обязательный TLS к удаленной СУБД, целостность capability, дедупликация, неполная копия, повреждение данных и манифеста, попытки выхода из дерева, единственный писатель и резерв свободного места.

Файловый цикл включает большой файл размером больше одного блока, пустой файл, внутреннюю символическую ссылку, права 0640, повторное копирование без новых блоков, удаление файла между точками, восстановление и отказ от перезаписи существующего назначения.

Для управления проверены создание задания через API, очередь, восстановление на отдельный путь, параллельность при лимите два, ожидание третьей операции, отмена, запрет второго управляющего процесса, идемпотентность, конфликты повторного ключа и отсутствие накопления повторных плановых запусков.

Проверки полномочий включают отсутствие клиентского сертификата, неверную роль сервера, отзыв сертификата на существующем соединении, отказ изменения аудитору, Origin и защитные атрибуты cookie веб-сессии.

В отчетах проверены XML-структура XLSX, отсутствие формульных ячеек, защита CSV от формул, экспорт 205 операций при размере страницы один, фильтрация и отдельная плановая дата будущего запуска.

## Проверка запущенного стенда

Через собранный CLI созданы и выполнены реальное файловое задание и восстановление. Содержимое восстановленного файла сравнено с исходником побайтово. Повторный инкрементальный запуск сохранил `verified: true`, `changed_files: 0`, `uploaded_bytes: 0`. Два запроса с одним `--idempotency-key` вернули один ID операции.

В браузере проверены парольный вход, история, подробности операции, заполнение формы задания зарегистрированными узлами, скачивание XLSX, раздел хранилищ, навигация на ширине 768 px и выход. Необработанных ошибок JavaScript и горизонтального переполнения на проверенной ширине не обнаружено. Изолированный браузер проверки допускал только для своего сеанса локальный сертификат разработки; настройки доверия ОС не изменялись.

Выгруженный из работающего сервиса XLSX дополнительно проверен как ZIP с корректными XML-частями и 14 колонками, включая `planned_at`.

## Сборка и границы выводов

Собраны `bin/srk` для macOS ARM64 и статический `bin/srk-linux-amd64` без CGO. Кросс-компиляция подтверждает сборку под Linux, но не испытания на ALT Linux или ROSA.

Испытания на IBM TS4300/LTO-9, СХД заказчика и Тионикс не проводились; их адаптеры еще не реализованы. Прикладная согласованность, RPO/RTO, безопасная физическая очистка, импорт и полный объем ТЗ этой проверкой не подтверждаются. Текущие ограничения перечислены в `implementation.md`.

Удаленные Git-репозитории не настроены. `.local/`, приватные ключи, пароль, бинарники и промежуточные материалы проверены как исключенные из Git.

# Дополнение: версия 0.4 — непрерывный WAL и PITR

Дата: 28 октября 2026 года. Финальный общий прогон с `SRK_TEST_PG_BIN`, `SRK_TEST_SRK_BIN`, отдельным `SRK_TEST_DATABASE_URL`, `-race`, `-count=1` и `-timeout 300s` успешно выполнил все 55 тестов верхнего уровня. `go vet ./...` завершился без ошибок. Собраны macOS ARM64 и статический Linux AMD64; YAML OpenAPI 0.4 разобран отдельно.

Нативный тест поднимает отдельный PostgreSQL 16.15 с сегментами WAL по 1 МиБ, включает настоящий `archive_command`, использует отдельный сертификат роли `wal` и передает файлы через CLI, агент и mTLS медиасервера. После базовой копии выполняются две транзакции по обе стороны цели. PITR достигает цели, останавливает кластер, затем отдельный тестовый запуск возвращает SQL-результат: запись до цели есть, записи после цели нет. Исходная база сохраняет обе транзакции. Для цели за пределами имеющихся commit-записей PostgreSQL возвращает `recovery ended before configured recovery target was reached`; система не присваивает успех.

Проверки репозитория охватывают повторы WAL, конфликт одного имени с разным содержимым, другую систему PostgreSQL, неполный сегмент, повреждение сохраненных байтов, пропуск, rollover номера WAL, ветвление timeline и сохранение WAL при обычном snapshot GC. Проверены привязка read-grant к архиву базовой копии и отказ роли `wal` в общей диагностике/запуске заданий. Производитель WAL не может подменить ID записи аудита управления через заголовок запроса.

Параметры PITR сохраняются в задании. Повтор с тем же ключом идемпотентности и другой целью дает конфликт. При этой проверке устранено переиспользование вложенных указателей при чтении сохраненного запроса каталога: сравнение теперь действительно различает как PITR, так и параметры обслуживания. Отдельная проверка подтверждает отмену активного HTTP-запроса при штатной остановке сервиса, необходимую для отмены дочернего recovery.

На работающем локальном стенде подготовлен отдельный демонстрационный PostgreSQL на порту 55433. Создана новая WAL-связанная базовая копия. Через веб-интерфейс просмотрены статус архивирования и реальные записи WAL, выбраны время и inclusive, поставлен и успешно выполнен PITR. Ответ содержит `result.pitr.recovered: true`. Восстановленный каталог дополнительно запущен на отдельном порту 55434 с тестовым loopback-доступом: SQL подтвердил `before-target = 1`, `after-target = 0`. Кластер снова остановлен, тестовый HBA-файл удален. Системный каталог управления на 55432 не перезапускался.

В браузере проверены форма PITR, подтверждение результата, архив WAL и ширина 768 px. Необработанных ошибок JavaScript и горизонтального переполнения не обнаружено. XLSX из работающего сервиса содержит 29 колонок; XML-части разобраны, архив, целевое время и признак подтвержденного PITR найдены. Проверен отдельный аудит `wal.archive` с производителем `agent/agent-local`.

Четыре сервиса СРК оставлены работающими в версии 0.4.0. Дополнительный демонстрационный источник PostgreSQL после испытаний остановлен, чтобы не создавать бесконечный тестовый WAL. Его данные находятся в игнорируемом `.local/postgresql-pitr`, базовая копия и архив — в репозитории, итог PITR — в `.local/restores/pitr-v04`. Для повторного запуска этого конкретного локального источника:

```sh
pg_ctl -D .local/postgresql-pitr -l .local/logs/pitr-source.log -o '-h 127.0.0.1 -p 55433 -k /tmp' -w start
```

Архивирование завершенных сегментов не гарантирует сохранение каждого commit в момент его выполнения. Поддерживается одна timeline, без автоматического экспайринга WAL; большой WAL-каталог, другие версии PostgreSQL/ОС, расширения, промышленные нагрузки и численные RPO/RTO требуют дальнейших испытаний. Инструкция — `wal-pitr.md`.

Новые зависимости не добавлены: инвентаризация лицензий остается на 55 зависимостях. Лицензия Apache 2.0 и авторство сохранены. Git remote не настроен; приватные ключи, конфиги, WAL, восстановленные данные и материалы проверок исключены из Git.

## Проверка 0.5 и аварийного образа

Добавлены проверки одноразового кода (включая восемь конкурентных попыток), ограниченной области копий и блоков, отзыва сессии, несовпадающего TLS-отпечатка и запрета write-capability у менеджера. Интеграционный тест проходит через настоящий HTTPS менеджер → mTLS media → проверенный RAW-файл с полным чтением после записи. Отдельный тест проверяет агентское сохранение offline RAW, отказ при лишних файлах и символической ссылке. Повреждённый блок отвергается до записи, слишком маленькая цель и отмена не игнорируются.

WAL: тестируются зависимые и просроченные физические базы, active pins, устаревший план, явное разрешение orphan archive, неизвестный WAL, повреждённый сегмент, восстановление частично выполненного перемещения в карантин после перезапуска и идемпотентная квитанция с привязкой к плану. Календарь проверяется на пропуск и отсутствие доверенных временных меток. Контрактные HTTPS-тесты четырёх VM API и защитные правила LTO выполняются без доступа к реальному оборудованию.

Полный набор race-тестов с отдельным PostgreSQL `srk_test`, `go vet`, статическая Linux amd64 сборка проходят. Полный native PostgreSQL набор (pg_basebackup/pg_verifybackup/pg_waldump/PITR) после интеграции rescue занял около 143 секунд. Локальный browser-тест проверил тип RAW-задания, календарь, предварительную очистку, выпуск и отзыв rescue-кода, ширину 768 px; необработанных JS-ошибок не было. Секрет кода в сохранённых скриншотах отсутствует.

ISO собран через Docker; El Torito содержит BIOS и UEFI entries. QEMU smoke-тесты обеих загрузок проверяют меню, виртуальный диск, логический сектор 512 байт, DHCP, /proc и /sys, версию 0.5.0. Тестовые устройства — только файлы внутри контейнера; реальные диски машины не подключались. Это не аппаратная сертификация физического сервера и не доказательство загрузки восстановленной конкретной ОС. Secure Boot и дополнительная vendor firmware не проверялись.

Команды повторения:

```
make rescue-iso
python3 scripts/smoke-rescue.py bios
python3 scripts/smoke-rescue.py uefi
SRK_TEST_DATABASE_URL=postgres://… go test -race ./...
go vet ./...
```

Финальный ISO дополнительно проверяется на обычном локальном экране и вводом виртуальной клавиатуры; включён Unicode-шрифт для кириллицы. В CSV/XLSX версии 0.5 добавлена 30-я колонка `wal_removed`; архив обслуживания отражается в `wal_archive_id`. Native-тест календаря дополнительно подтвердил временную границу COMMIT после выбранной цели и корректный PITR (около 79 секунд).

## Версия 0.6 — прямая копия физического диска
