# Непрерывный WAL и PITR — версия 0.4

PostgreSQL передает завершенные WAL-сегменты через штатный `archive_command`. Команда вызывает ограниченный API агента; агент читает только `pg_wal` настроенного кластера и передает файл медиасерверу по mTLS. PostgreSQL получает код успеха только после сохранения данных, метаданных и аудита медиасервера. При недоступности сервиса PostgreSQL сохраняет исходный WAL и повторяет архивирование своим штатным механизмом.

PITR — отдельный вариант восстановления базовой копии: система проверяет принадлежность и последовательность WAL, восстанавливает базу в новый каталог, запускает изолированное recovery до заданного времени, подтверждает достижение цели и останавливает полученный кластер. Возврат конца доступного архива вместо недостижимой цели не считается успехом.

## Конфигурация агента

К существующему PostgreSQL-профилю добавляется `wal_archive`:

```json
{
  "postgresql": {
    "production": {
      "host": "postgres.internal.example",
      "port": 5432,
      "user": "srk_backup",
      "database": "postgres",
      "sslmode": "verify-full",
      "sslrootcert": "/etc/srk/postgresql-ca.crt",
      "passfile": "/etc/srk/postgresql.pgpass",
      "bin_dir": "/usr/lib/postgresql/16/bin",
      "staging_dir": "/var/lib/srk/postgresql-staging",
      "timeout_seconds": 7200,
      "wal_archive": {
        "data_dir": "/var/lib/postgresql/16/main",
        "media_id": "media-main",
        "media_url": "https://media.internal.example:8444"
      }
    }
  }
}
```

Это фрагмент конфигурации. Агент архивирования должен работать на хосте PostgreSQL и иметь доступ к файлам этого кластера. Профиль подключения должен указывать на тот же кластер, что и `data_dir`. PostgreSQL-пользователь для базовой копии сохраняет ограниченные replication-права. Права ОС на чтение `PGDATA` выдаются отдельно; SQL-роль не заменяет их.

Нужен полный комплект утилит соответствующей основной версии: `pg_basebackup`, `pg_verifybackup`, `pg_waldump`, `pg_controldata`, `postgres`, `pg_ctl`. Данные и бинарники должны иметь совместимые версию, архитектуру и формат. Полный цикл испытан на PostgreSQL 16.15. Другие принимаемые версии 13–18 требуют собственных приемочных испытаний.

## Ограниченный клиент archive_command

Создайте отдельный сертификат роли `wal`. Его ID должен быть равен ID агента с суффиксом `-wal`, например `agent-db-wal` для `agent-db`:

```sh
bin/srk pki issue --dir /secure/ca --installation office-main --role wal --id agent-db-wal
```

CA и его приватный ключ остаются у администратора. PostgreSQL-процесс получает только клиентские сертификат и ключ, доверенный CA, файл отзывов и следующий клиентский конфиг, доступные ему с минимальными правами:

```json
{
  "role": "wal",
  "id": "agent-db-wal",
  "installation": "office-main",
  "url": "https://agent-db.internal.example:8445",
  "ca": "/etc/srk/wal-client/ca.crt",
  "cert": "/etc/srk/wal-client/agent-db-wal.crt",
  "key": "/etc/srk/wal-client/agent-db-wal.key",
  "revoked_file": "/etc/srk/wal-client/revoked.json"
}
```

Приватный ключ и клиентский конфиг — `0600` или `0400`. Сертификат роли `wal` позволяет только запросить архивирование файлов настроенных профилей своего агента: он не позволяет запускать задания, читать резервные копии или обращаться к общей диагностике агента. В медиасервер пишет сам агент своим сертификатом. Личный административный сертификат в `archive_command` не используется.

## Настройка PostgreSQL

Пример для стандартных Unix-путей:

```conf
archive_mode = on
archive_timeout = '60s'
archive_command = '/usr/local/bin/srk --config /etc/srk/wal-client/client.json --timeout 120s agent wal archive production --file "%p" --name "%f"'
```

Изменение `archive_mode` требует перезапуска PostgreSQL, изменение команды — перечитывания конфигурации. Система не меняет и не перезапускает рабочий PostgreSQL автоматически. Сначала проверьте команду и права ОС, затем включите архивирование и создайте **новую базовую копию** профиля с `wal_archive`. У старых копий версии 0.3 нет привязки к этому архиву; обычное восстановление для них сохраняется.

Архивирование непрерывно обслуживается процессом PostgreSQL, но отправляет завершенные сегменты, а не каждый WAL record. Задержка зависит от переключения сегмента, `archive_timeout`, сети и подтверждения хранилища. Само значение `60s` не является гарантией RPO. Для проверки передачи только в управляемом испытании можно вызвать `SELECT pg_switch_wal()`; состояние сервера доступно в `pg_stat_archiver`.

Если архивирование постоянно завершается ошибкой, PostgreSQL удерживает WAL на исходном диске. Следите за `pg_stat_archiver`, статусом агента и свободным местом источника и медиасервера: переполнение `pg_wal` может остановить исходный PostgreSQL.

## Идентичность и целостность

Новая базовая копия сохраняет `system_id`, размер сегмента и `archive_id`. Архивное пространство вычисляется из ID агента, имени профиля и PostgreSQL system identifier. Кластеры с одинаковыми именами профиля не смешиваются. Смена ID агента или имени профиля создает другое пространство архива и требует новой базовой копии.

При получении сегмента проверяются его полная длина, длинный заголовок, system identifier, геометрия, timeline и начальная позиция. Файл сохраняется с SHA-256 и контрольной суммой метаданных. Полная проверка WAL records выполняется самим PostgreSQL при recovery. Частичные `.partial` не публикуются. Также сохраняются штатные `.history` и `.backup`-файлы.

Повторное сохранение одинакового имени и содержимого идемпотентно. Разное содержимое под прежним именем вызывает ошибку. При чтении медиасервер заново проверяет SHA-256. Получение WAL для восстановления дополнительно ограничивается подписанным разрешением, связанным с выбранной базовой копией и ее архивом.

## Интерфейс и CLI

В карточке агента показаны настроенные архивы, последнее подтверждение и последняя ошибка. «Посмотреть архив» показывает последние записи и время сохранения. Это время подтверждения приема, **не** время последней транзакции и не обещание доступной границы PITR.

```sh
bin/srk --config .local/admin.json --json manager nodes
bin/srk --config .local/admin.json --json manager wal list MEDIA_ID ARCHIVE_ID
bin/srk --config .local/media.json --json media wal list ARCHIVE_ID
```

В форме восстановления новой WAL-связанной PostgreSQL-копии включите PITR и укажите время в локальном часовом поясе. API/CLI используют RFC3339 с явным часовым поясом; время нормализуется в UTC с точностью PostgreSQL до микросекунд. По умолчанию включается транзакция, время commit которой точно равно цели. В интерфейсе или через `--exclusive` можно исключить ее.

```sh
bin/srk --config .local/admin.json --json --wait --timeout 2h manager runs restore BASE_RUN_ID \
  --destination /var/lib/srk/restores/postgres-pitr-001 \
  --target-time '2026-10-28T12:30:00+03:00'
```

HTTP-запрос:

```json
{
  "destination": "/var/lib/srk/restores/postgres-pitr-001",
  "pitr": {
    "target_time": "2026-10-28T12:30:00+03:00",
    "inclusive": true
  }
}
```

Он отправляется на `POST /v1/runs/BASE_RUN_ID/restore`. Время должно быть после окончания базовой копии и не в будущем. Изменение цели с прежним ключом идемпотентности отклоняется как конфликт. Принятие в очередь еще не означает достижение цели: проверяйте итог `status: success`, `result.pitr.recovered: true` и подтвержденное время в результате.

## Что делает восстановление

1. Проверяет доступность базовой копии и выбранную цель, восстанавливает файлы и выполняет `pg_verifybackup`.
2. Читает архив нужного кластера и проверяет последовательность сегментов с учетом WAL из самой базовой копии. Пропуск прерывает работу. Из архива загружаются сегменты основной timeline начиная с нужного базовой копии сегмента; каждый файл проверяется по SHA-256.
3. Сохраняет исходные конфигурационные файлы в `srk_original_config/` и создает минимальную конфигурацию. Исходные includes, preload-библиотеки, archive/recovery-команды и параметры публикации не выполняются автоматически.
4. Запускает PostgreSQL без TCP-порта. Нужный самому PostgreSQL Unix-сокет находится в отдельном каталоге `0700`, а `pg_hba.conf` запрещает все SQL-подключения. Задает точную timeline, `recovery_target_time`, inclusive и `recovery_target_action=promote`.
5. Требует сообщения PostgreSQL о достижении цели и завершении запуска, останавливает процесс, проверяет system identifier, чистое состояние `shut down` и отсутствие `recovery.signal`. Сохраняет `srk-pitr-result.json` и выставляет успешный итог.

Итог — **остановленный кластер на целевом состоянии**, а не только подготовленный `recovery.signal`. TCP-порт и права подключения для дальнейшего использования настраивает оператор. Конфигурация по умолчанию остается закрытой. Проверяйте расширения и параметры приложения перед публикацией восстановленной базы.

Цель, статус подтверждения и архив отображаются в истории и CSV/XLSX. JSON-результат дополнительно содержит число загруженных сегментов. Журнал самого recovery находится в `srk-pitr.log` нового каталога. После replay файлы данных уже отличаются от исходного backup manifest: нативная проверка базовой копии проводится **до** replay, а достижение цели подтверждается отдельно. При ошибке частичный новый каталог сохраняется для диагностики и не считается пригодным PITR-результатом. Штатная остановка агента отменяет активные запросы и дочерний recovery; после аварийного уничтожения процесса проверьте `postmaster.pid` и журнал нового каталога перед любыми дальнейшими действиями.

## Текущие границы

Поддерживается одна timeline базовой копии. Обнаружение более новой timeline в архиве требует новой базовой копии; переход через ветвления пока не реализован. Снимки с дополнительными tablespace и восстановление приложений, требующих preload-библиотек во время replay, требуют отдельной поддержки и испытаний.

WAL сохраняется независимо от блочного хранилища копий и **не удаляется обычной очисткой snapshots/chunks**. Автоматический dependency-aware экспайринг WAL пока не реализован; удаление по одному только возрасту было бы небезопасно для PITR. Планируйте емкость и контролируйте свободное место. WAL учитывается отдельно от экономии дедупликации файловых копий. Пропуск, отсутствующий носитель, повреждение и недостижимая цель дают ошибку, а не частично успешное восстановление.

Долговременное массовое архивирование и большие каталоги WAL требуют отдельной приемки производительности; постраничный WAL-каталог пока не реализован. Не заявляются нулевая потеря при утрате незавершенного сегмента, синхронная репликация, архивирование на ленты и выполнение 3-2-1 этим единственным контуром.

## Проверка

```sh
make build
SRK_TEST_PG_BIN=/absolute/path/to/postgresql/16/bin \
SRK_TEST_SRK_BIN=/absolute/path/to/gdata/bin/srk \
SRK_TEST_DATABASE_URL='postgres://TEST_USER@127.0.0.1:55432/srk_test?sslmode=disable' \
go test -race -count=1 -timeout 300s ./...
```

Нативный тест использует отдельный временный кластер и настоящий `archive_command`, проверяет транзакции до/после цели, независимость исходной БД и отказ для недостижимой цели. Отдельно проверяются пропуски, другой кластер, повреждения, повторная передача, права сертификатов и ключи идемпотентности.

Основные механизмы PostgreSQL: [непрерывное архивирование](https://www.postgresql.org/docs/16/continuous-archiving.html), [параметры recovery](https://www.postgresql.org/docs/16/runtime-config-wal.html).

## 0.5: безопасная очистка и календарь

WAL удаляется отдельным обслуживанием, а не обычной очисткой дедуп-блоков. `manager wal gc-preview MEDIA_ID ARCHIVE_ID --before RFC3339 [--allow-orphan]` возвращает план; сохраните и проверьте JSON, затем примените `manager wal gc MEDIA_ID ARCHIVE_ID --plan FILE --confirm`. Через media доступны те же команды без MEDIA_ID. HTTP-план действует 15 минут; manager выполняет его через общую очередь. В интерфейсе: архив WAL → календарь PITR → предварительная очистка.

Защита учитывает все физически существующие базовые копии архива, включая просроченные, пока они не удалены. Сохраняется цепочка начиная с самого раннего нужного сегмента каждого timeline; неизвестные ветви сохраняются. Создание новой WAL-связанной базы предварительно устанавливает долговечную защиту архива. Незнакомые или повреждённые метаданные блокируют удаление. Архив без баз требует отдельного явного разрешения; последний сегмент каждого timeline, `.history` и `.backup` сохраняются. Возраст удаления не менее 24 часов. Автоматический WAL GC по расписанию пока не включён.

При применении заново сверяются состав, метаданные, физические файлы, защиты и сам план; проверяется SHA-256 удаляемых сегментов. Перемещение в карантин и удаление журналируются с восстановлением после перезапуска. Повтор того же operation ID возвращает сохранённый результат только для того же плана.

Календарь показывает предварительные интервалы по непрерывной цепочке и временным меткам COMMIT, извлечённым `pg_waldump` с UTC. Время архивации не считается временем транзакций. Старые WAL без этих метаданных имеют неизвестную временную границу: повторная загрузка не переписывает существующие метаданные. Верхняя граница исключающая, точную достижимость подтверждает native recovery. Нужна синхронизация часов агента и СУБД; скачки времени помечаются ошибкой/неизвестностью. Пропуски показываются по LSN и количеству сегментов, а не выдуманным временным интервалом. Восстановление разрешается только из непрерывного префикса до первого разрыва; цель за ним завершается ошибкой PostgreSQL. Автоматический переход между timeline всё ещё не реализован.
