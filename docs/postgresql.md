# Горячий PostgreSQL

Система создает физическую полную копию работающего кластера PostgreSQL. Запросы продолжают выполняться: агент запускает `pg_basebackup` с `--wal-method=stream`, получает необходимые для этой копии WAL и проверяет результат через `pg_verifybackup`, включая разбор WAL штатным `pg_waldump`. Затем файлы передаются по mTLS в существующий дедуплицируемый репозиторий. Успешный результат появляется после подтверждения медиасервера.

Это копия всего кластера, включая все базы и глобальные объекты. Выбор одной базы, логический `pg_dump` и инкрементальная физическая копия пока не реализованы. Обычное восстановление возвращает согласованное состояние полученной базовой копии. Версия 0.4 дополнительно поддерживает [непрерывное архивирование и PITR](wal-pitr.md) для новых копий с привязкой к WAL-архиву.

## Подготовка

На агенте нужны `pg_basebackup`, `pg_verifybackup`, `pg_waldump` той же основной версии, что и сервер. Реализация принимает версии 13–18; полный интеграционный цикл испытан на PostgreSQL 16.15. Проверка других версий на целевых ОС остается приемочным испытанием.

Учетной записи подключения нужен атрибут `LOGIN REPLICATION` и разрешение replication-подключения с адреса агента в `pg_hba.conf`. Потоковый WAL использует второе replication-соединение; нужны свободные `max_wal_senders` и `max_replication_slots`. Используется временный слот штатной утилиты, постоянный слот система не создает. Параметры PostgreSQL и учетные записи рабочего сервера автоматически не меняются. Контрольная точка запрашивается в режиме `fast`, что может увеличить дисковую нагрузку.

Создайте отдельный каталог staging с правами `0700` и достаточным местом приблизительно для двух несжатых копий: сначала архивов, затем распакованной и проверяемой базы. `reserve_bytes` агента задает запас свободного места; значение по умолчанию — 1 ГиБ. Это проверяемый порог, а не квота файловой системы. Во время получения проверяется доступное место, при распаковке — место под каждый файл. Для жесткого ограничения нужны отдельный том или системная квота.

Добавьте в конфигурацию **агента**, например `/etc/srk/agent.json`:

```json
{
  "postgresql": {
    "production": {
      "host": "postgres.internal.example",
      "port": 5432,
      "user": "srk_backup",
      "database": "postgres",
      "sslmode": "verify-full",
      "sslrootcert": "/etc/srk/postgresql-ca.crt",
      "passfile": "/etc/srk/postgresql.pgpass",
      "bin_dir": "/usr/lib/postgresql/16/bin",
      "staging_dir": "/var/lib/srk/postgresql-staging",
      "timeout_seconds": 7200
    }
  }
}
```

Это фрагмент: остальные настройки агента сохраняются. Пути абсолютные, timeout — от 1 до 36000 секунд. Бинарники должны быть исполняемыми. `pgpass` имеет формат libpq и права `0600` или `0400`; для replication-подключения поле базы — `replication`. Пароль не включается в задания, аргументы процесса, API, аудит и отчеты. На стенде с `development: true` разрешен `sslmode: disable` исключительно для loopback-адреса. В промышленной конфигурации обязательны `verify-full` и явный CA-файл.

Именованный профиль локален агенту. Управление получает только его имя через heartbeat. Произвольные DSN, пароли и адреса из задания не принимаются. После изменения конфигурации перезапустите агент и дождитесь обновления его статуса.

## Задание и CLI

Пример файла задания:

```json
{
  "type": "postgresql",
  "name": "PostgreSQL production",
  "agent_id": "agent-db",
  "media_id": "media-main",
  "source": "postgresql://production",
  "mode": "full",
  "interval_seconds": 86400,
  "retention_days": 30,
  "enabled": true
}
```

```sh
bin/srk --config .local/admin.json --json manager jobs create --file /absolute/path/job-postgresql.json
bin/srk --config .local/admin.json --json --wait --timeout 2h manager jobs run JOB_ID
bin/srk --config .local/admin.json --json manager runs get RUN_ID
```

В веб-форме выберите «PostgreSQL · горячая копия», агент с настроенным профилем и источник `postgresql://production`. Для PostgreSQL разрешен только полный режим. Задания используют общую очередь, ограничения параллельности, расписание, отмену и историю.

Этап получения показывает процент, сообщаемый `pg_basebackup`. Распаковка имеет отдельный процент по прочитанному объему архивов. При нативной проверке отображается выполняющийся этап без выдуманного процента. Передача проверенного staging в репозиторий имеет отдельный процент по оцененному объему. 100% всей операции возвращается только после успешной проверки и фиксации. Промежуточные результаты поступают через heartbeat, поэтому отображение может отставать примерно на несколько секунд.

В результате и манифесте сохраняются `consistency: postgresql-physical`, основная версия, имя профиля, время получения копии, диапазоны LSN/timeline и подтверждение нативной проверки. CSV/XLSX дополнены этими сведениями. Повторная операция «Проверить» на медиасервере проверяет целостность сохраненных блоков; нативная проверка PostgreSQL дополнительно выполняется при восстановлении.

## Восстановление

```sh
bin/srk --config .local/admin.json --json --wait --timeout 2h manager runs restore RUN_ID --destination /var/lib/srk/restores/postgres-recovery-001
```

Назначение — новый, несуществующий каталог внутри `restore_roots`. В агенте восстановления должен быть профиль с тем же именем и утилитами нужной основной версии. Для самого восстановления соединение с исходной БД не требуется. Агент восстанавливает файлы и повторно запускает `pg_verifybackup`, включая WAL. При ошибке каталог остается для диагностики и не считается пригодным восстановлением.

PostgreSQL автоматически не запускается, рабочая БД не останавливается и не перезаписывается. Перед контрольным запуском на изолированном сервере проверьте владельца файлов, версию PostgreSQL, расширения и скопированные настройки: `data_directory`, адреса и порт, пути SSL, `shared_preload_libraries`, `archive_command`, recovery-параметры и `pg_hba.conf`. При запуске явно задайте новый `data_directory`, отдельный порт и изолированные сетевые настройки. Не следует запускать копию с исходными параметрами публикации и внешних команд без их проверки.

Импорт собственного дискового репозитория сохраняет признак PostgreSQL и метаданные проверки; созданное импортом задание отключено. Удержание, сроки и очистка применяются к PostgreSQL-копиям так же, как к файловым.

## Ограничения и проверки

Дополнительные tablespace пока отклоняются. Получение сначала идет в tar-формате, поэтому утилита не пишет по исходным путям tablespace. До распаковки проверяется состав архивов; распаковка через `os.Root` запрещает выход из staging, ссылки, устройства и повторные файлы. Исходный сервер не изменяется. Staging удаляется после завершения или обрабатываемой ошибки; аварийное завершение процесса может оставить приватный `backup-*` для ручной диагностики и удаления после проверки отсутствия активной операции.

Изолированный тест создает новый PostgreSQL-кластер, пишет в него во время копирования, восстанавливает копию, запускает полученный кластер на отдельном порту и читает контрольные данные. Также проверяются отсутствие необходимого WAL, неподдерживаемый tablespace, очистка staging, ограниченные replication-права, отмена дочернего процесса, сохранение типа при импорте и отсутствие секретов в диагностике.

```sh
SRK_TEST_PG_BIN=/absolute/path/to/postgresql/16/bin \
SRK_TEST_DATABASE_URL='postgres://TEST_USER@127.0.0.1:55432/srk_test?sslmode=disable' \
go test -race -count=1 -timeout 180s ./...
```

`SRK_TEST_PG_BIN` включает тесты с временными кластерами и требует запуска без root. Существующий рабочий PostgreSQL тест не переинициализирует. Переменная `SRK_TEST_DATABASE_URL` относится только к отдельному тестовому каталогу управления.

Штатные механизмы: [pg_basebackup](https://www.postgresql.org/docs/16/app-pgbasebackup.html), [pg_verifybackup](https://www.postgresql.org/docs/16/app-pgverifybackup.html). Успешная проверка файлов и WAL дополняет контрольное восстановление, но не заменяет испытания приложения и численную приемку RPO/RTO.
