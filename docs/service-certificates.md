# Сервисные сертификаты: сроки, продление и ротация

Версия 0.10.0. Роли manager, media, agent и proxy автоматически получают новый
сертификат с новым ключом без перезапуска процесса. Существующие инсталляции
продолжают использовать прежние файлы до явного включения функции.

## Уведомления

Администратор видит кнопку «Сервисные сертификаты», список сроков и сообщение
при наличии проблем. Оповещения появляются за 30 дней, становятся критическими
за 7 дней и показывают истечение срока. Ошибка продления и отсутствие свежего
heartbeat также требуют внимания. Интерфейс обновляет уведомления каждые
30 секунд, менеджер проверяет сроки раз в минуту.

Срок и серийный номер удалённого компонента менеджер получает из фактического
клиентского сертификата mTLS при heartbeat. Присланные в JSON сроки не заменяют
эти сведения. Для давно отключённого узла показываются последние наблюдения
с отметкой об их давности. До первого heartbeat срок узла неизвестен.

События `certificate.alert` сохраняются в аудите и в структурированном журнале
менеджера. Повторный опрос не создаёт повторное событие для того же сертификата
и состояния. События выдачи `service_certificate.issued` фиксируются в одной
транзакции с реестром поколений. Уведомления реализованы в интерфейсе, API,
CLI и журналах; отправка электронной почты или сообщений не настраивается.

```sh
srk --config /secure/admin.json --json manager service-certificates
srk --config /etc/srk/agent.json --json agent certificate status
journalctl -u srk@manager --since today
```

Список сервисных сертификатов доступен только администратору. Персональные
пользовательские сертификаты управляются отдельно по
[инструкции](recovery-access-and-certificates.md).

## Настройка менеджера

В конфигурацию менеджера добавьте путь к закрытому ключу CA, которым подписаны
начальные сервисные сертификаты. Ключ должен соответствовать `ca`, иметь права
0600/0400 и быть доступен сервисному пользователю. Он остаётся на менеджере.
Если CA должен оставаться полностью офлайн, автоматическую выдачу не включайте.

```json
{
  "service_ca_key_file": "/etc/srk/service-ca.key",
  "service_certificates": {
    "directory": "/var/lib/srk/certificates/manager",
    "auto_renew": true,
    "renew_before_hours": 720,
    "lifetime_hours": 2160
  }
}
```

Это дополнение к полной конфигурации, а не самостоятельный файл. Менеджеру
нужен доступ к собственному HTTPS-адресу `url`; имя должно присутствовать в SAN
его сертификата. `lifetime_hours` менеджера также ограничивает максимальный
срок, который могут запросить остальные компоненты.

## Настройка агентов, медиасерверов и прокси

На каждом компоненте задайте собственный каталог и адрес менеджера:

```json
{
  "manager_url": "https://manager.example.org:8443",
  "service_certificates": {
    "directory": "/var/lib/srk/certificates/agent",
    "auto_renew": true,
    "renew_before_hours": 720,
    "lifetime_hours": 2160
  }
}
```

Закрытый ключ CA на эти машины не переносится. Каждый каталог принадлежит
только соответствующему компоненту. При размещении нескольких ролей на одной
машине им нужны разные каталоги. Создайте каталоги от root, например:

```sh
install -d -m 0700 -o srk -g srk /var/lib/srk/certificates/agent
runuser -u srk -- srk --config /etc/srk/agent.json agent check-config
```

Стандартный systemd unit разрешает запись в `/var/lib/srk`. Конфигурация и
начальные `cert`/`key` могут оставаться в защищённом `/etc/srk`. Для перехода
на новую версию и первичного включения настроек требуется обычное обновление
и запуск служб. Последующие продления и смены ключа выполняются без рестартов.

По умолчанию срок равен 2160 часам (90 суток), порог продления — 720 часам
(30 суток). Допустим срок 2–2160 часов и положительный порог меньше срока.
После старта компонент проверяет срок через секунду, затем каждую минуту.
После ошибки повторяет попытку через пять минут. Выдача не сокращает срок
текущего сертификата и не выходит за срок действия CA. Запрос до нужного
окна с меньшим сроком отклоняется, оставляя текущий сертификат.

## Протокол и непрерывность работы

1. Компонент создаёт новый ключ P-256 и сохраняет его в `pending.key` с правами
   0600 до отправки запроса. Одновременные локальные ротации блокируются.
2. По mTLS компонент отправляет CSR на `POST /v1/service-certificates/renew`.
   Менеджер сохраняет установку, роль, ID и DNS/IP SAN из удостоверенного
   текущего сертификата. Поля идентичности и SAN из CSR не расширяют полномочия.
3. Реестр PostgreSQL сериализует выдачу. После потерянного ответа повтор с тем
   же ожидающим ключом возвращает тот же сертификат. Старый сертификат не может
   получить другое следующее поколение. В период аварийного восстановления
   каталога выдача приостановлена до административной проверки.
4. Компонент проверяет цепочку, ключ, идентичность, адреса и срок. Новая пара
   сохраняется в один `current.pem` атомарным переименованием после `fsync`.
   TLS видит полностью старую либо полностью новую пару.
5. Новые входящие TLS-соединения используют новый сертификат. Исходящие клиенты
   закрывают свободные соединения при переключении и раз в минуту. Занятые
   потоки не прерываются. Сертификат исходящего клиента выбирается динамически
   при следующем соединении. TLS session tickets для этого режима отключены.
6. После успешного переключения ожидающий ключ удаляется. Перезапуск процесса
   использует `current.pem`; исходные `cert`/`key` не перезаписываются.

Ошибка выдачи или проверки не заменяет рабочую пару. Ошибка отражается в
статусе компонента и журнале. Каталог сертификатов и исходные файлы входят в
состав эксплуатационной конфигурации и должны сохраняться при обновлении.
Не удаляйте `pending.key`, если выдача могла завершиться, а ответ потерялся.

Ротация не отзывает прежний сертификат автоматически: он сохраняет доверие до
своего `NotAfter` или явного отзыва. Это позволяет завершаться старым потокам.
Старое поколение после выдачи следующего не допускается к новой ротации другим
ключом. При компрометации используйте штатный отзыв и административный выпуск;
обычная автоматическая ротация не заменяет процедуру реагирования.

## Ручной запуск и восстановление после ошибок

Немедленно запросить новый ключ и сертификат можно от имени самого компонента:

```sh
runuser -u srk -- srk --config /etc/srk/agent.json agent certificate renew
```

Команда требует настроенный каталог и действующий сервисный сертификат. Даже
при `auto_renew: false` она выполняет разовую ротацию. Вручную слишком ранний
запрос может быть отклонён, если запрошенный срок сократил бы текущий.

Истёкший или отозванный сертификат автоматически не восстанавливается: mTLS
не ослабляется. Администратор выпускает сертификат и новый ключ прежней
идентичности, сверяет реестр и восстанавливает согласованное состояние. Если
рабочий ключ и `pending.key` утрачены после зафиксированной выдачи, требуется
административная сверка реестра; произвольный новый ключ старым сертификатом
сервер не примет. Сохраните материалы и аудит для диагностики.

Для утраченного ожидающего ключа или истёкшей идентичности предусмотрены
административные команды. Выпустите офлайн новую пару прежней роли/ID и с
нужными SAN, используя тот же доверенный CA. Срок нового сертификата должен
оставаться в пределах CA. На менеджер передаётся только публичный сертификат:

```sh
srk --config /secure/admin.json --json manager service-certificates
srk --config /secure/admin.json manager service-certificates adopt \
  --file /secure/new-agent.crt --expected-serial REGISTERED_SERIAL \
  --reason 'Восстановление после утраты ожидающего ключа'
```

`REGISTERED_SERIAL` — последняя выдача `registered_serial` из инвентаря, которая
может отличаться от наблюдаемого серийного номера при потере ответа. Для первой
регистрации используйте пустую строку. Операция требует администратора, причины
и совпадения текущего поколения, записывается в аудит вместе с изменением
реестра. Сертификат должен быть действующим, неотозванным и подписанным CA этой
установки. Ранее выданные сертификаты не получают право продлеваться после
принятия новой пары. Для собственного менеджера последнюю выдачу также показывает CLI.

На целевом компоненте установите пару в настроенный writable-каталог:

```sh
runuser -u srk -- srk --config /etc/srk/agent.json agent certificate install \
  --cert /secure/new-agent.crt --key /secure/new-agent.key
```

Ключ имеет права 0600/0400 и остаётся на компоненте. Команда проверяет CA,
идентичность, адрес `url` и соответствие ключа, заменяет `current.pem` атомарно
и удаляет прежний `pending.key`. Динамическая загрузка применяет пару без
рестарта. Если истёк сертификат самого менеджера и его HTTPS уже недоступен,
сначала установите его новую пару локальной командой `manager certificate
install`, затем примите её в реестре через административный CLI. После
аварийного восстановления каталога предварительно завершите административную
проверку восстановления. Проверьте соединения и сделайте новый архив каталога.

Корневой CA автоматически не продлевается и не меняет ключ. Его срок входит
в уведомления. Планируйте смену доверенного CA отдельно до его истечения.

## Каталог и совместимость архивов

Архив каталога 0.10.0 включает реестр сервисных сертификатов, фактически активный
ключ/сертификат менеджера и настроенный ключ сервисного CA. Если поколение
менеджера в PostgreSQL ещё не совпадает с установленным на диске, резервирование
каталога завершается ошибкой с требованием повторить после завершения ротации.
Архив не публикуется в несогласованном состоянии.

Восстановленная конфигурация использует сохранённую активную пару. Автоматическая
ротация отключена до выбора нового writable-каталога и проверки администратора.
Ключи остальных узлов остаются на самих узлах и в архив каталога не входят.

Добавлена таблица `srk_service_certificates`. Формат резервирования по-прежнему
проверяет точную версию и схему. Архив 0.9.2 восстанавливают бинарником 0.9.2,
после чего выполняют обновление до 0.10.0. До обновления сохраните старый бинарник
и проверенный архив. Процедура: [аварийное восстановление](catalog-disaster-recovery.md).
