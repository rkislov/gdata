# Дисковые копии и жизненный цикл

Версия 0.2 добавляет учет экземпляров на диске, изменение срока хранения, удержание, импорт собственного формата СРК и физическую очистку неиспользуемых блоков. Операции доступны через систему управления, CLI и раздел «Хранилища» веб-интерфейса.

## Защита данных при очистке

Каждый репозиторий получает постоянный UUID в `repository.json`. Политика отдельной точки хранится в `state/ID.json`, независимо от неизменяемого манифеста. Запрет удаления (`hold`) имеет приоритет над истечением срока.

Активные потоки имеют устойчивые записи в `leases/`. Чтение удерживает выбранную точку, запись — свою базу. Пока есть незавершенная запись, удаление блоков целиком откладывается: часть этих блоков может еще не иметь опубликованного манифеста. Защита сохраняется после перезапуска медиасервера. Завершенные операции закрывают разрешение; оставшиеся после обрыва соединения разрешения прекращают действие по своему сроку, максимум через 12 часов.

Для копий с полным манифестом `base` описывает происхождение инкремента и не является обязательным внешним файлом восстановления. Очистка сохраняет каждый блок, на который ссылается хотя бы один оставшийся манифест. Поэтому просроченную базовую точку можно убрать, если следующая точка имеет полное представление и все необходимые блоки сохраняются.

Перед ручной очисткой читаются и проверяются манифесты, их политики и содержимое копий. Показываются конкретные точки, блоки, объем и ограничения активных потоков. План действует 15 минут и проверяется повторно под блокировкой репозитория. Изменение данных, политик или разрешений делает старый план неприменимым; нужно повторить расчет.

Изменения очистки записываются в `.gc/journal.json`. Файлы сначала перемещаются в карантин текущей операции, затем удаляются. После сбоя медиасервер продолжает журнал до допуска новых потоков. При повреждении журнала или ошибке его записи дальнейшие изменения блокируются. Файлы действующих копий при этом не считаются мусором. Запущенное обслуживание нельзя отменить через API; ожидающую операцию отменить можно.

`bytes_removed` — сумма размеров удаленных файлов блоков. Это не обещание немедленного увеличения свободного места на тот же объем и не гарантия уничтожения содержимого носителя. Актуальная свободная емкость показывается отдельно по файловой системе.

## CLI через управление

Глобальные флаги ставятся перед компонентом. Во всех командах ниже используется конфигурация администратора.

```sh
bin/srk --config .local/admin.json --json manager repository snapshots media-local
bin/srk --config .local/admin.json --json manager repository gc-preview media-local > .local/cleanup-plan.json
bin/srk --config .local/admin.json --json --wait --timeout 10m manager repository gc media-local --plan .local/cleanup-plan.json --confirm
```

Удержать точку или изменить ее срок:

```sh
bin/srk --config .local/admin.json --json --wait manager repository policy media-local SNAPSHOT_ID --hold true --reason 'Проверка восстановления' --confirm
bin/srk --config .local/admin.json --json --wait manager repository policy media-local SNAPSHOT_ID --expires '2027-01-01T00:00:00+03:00' --confirm
```

Снятие удержания выполняется той же командой с `--hold false --confirm`. Если срок уже истек, следующая очистка сможет удалить эту точку.

Команды медиасервера доступны напрямую через `--endpoint https://localhost:8444 media repository ...`, без `media-local` после команды. Для изменений нужен клиентский сертификат администратора. Прямой импорт на медиасервере проверяет данные и устанавливает удержание; регистрацию в центральном каталоге выполняет команда системы управления.

## Импорт после потери каталога или переноса диска

1. Остановить прежнего владельца записи. Новый медиасервер должен получить исключительную файловую блокировку репозитория.
2. Выдать новому компоненту сертификат текущей инсталляции и указать путь репозитория в его конфигурации. Старые учетные записи и задания из копии не исполняются.
3. Выполнить инвентаризацию. Выбрать существующие манифесты и зарегистрированный агент назначения восстановления.
4. Запустить импорт с явным новым минимальным сроком хранения.

```sh
bin/srk --config .local/admin.json --json --wait --timeout 10m manager repository import media-local --snapshots SNAPSHOT_ID --agent agent-local --retention-days 30 --confirm
```

Импорт проверяет все блоки выбранных точек, продлевает срок при необходимости и устанавливает удержание. В каталоге создаются новые локальные идентификаторы и отключенные задания без расписания. UUID репозитория, физический идентификатор точки и исходный идентификатор задания сохраняются как происхождение. Повторный импорт уже учтенной копии не создает дубликат; сохраненная копия не подменяется произвольной новой датой восстановления.

Просроченные, но еще физически существующие данные можно импортировать. Уже удаленные или перезаписанные блоки этим не возвращаются. После проверки восстановления оператор снимает удержание отдельно. Если регистрация в PostgreSQL оборвалась, защита на медиасервере остается; операцию можно повторить.

## Автоматическая очистка

В конфигурации управления задается `retention_interval_seconds`: `0` отключает автоматическую очистку, значения от `60` до `2592000` задают интервал. По умолчанию она отключена. После изменения конфигурации требуется перезапуск управления.

Автоматическая очистка разрешается только для UUID репозитория, уже известного каталогу по успешной копии или подтвержденному импорту на этом медиасервере. Подключение незнакомого диска и восстановление пустого каталога сами по себе не включают удаление данных. Нужны инвентаризация и принятие данных через импорт либо новая успешная копия. Это ограничение действует и при включенном интервале.

На каждом интервале создается одна операция очистки, а повтор после перезапуска в том же интервале не дублирует ее. Автоматические операции проходят через общую очередь, лимиты, историю и аудит управления. При активных писателях удаление блоков откладывается до последующей очистки.

## История и диагностика

Очистка, импорт и изменение политики отображаются в текущей активности и истории с собственными ID. Отчеты CSV/XLSX содержат UUID репозитория, состояние копии, числа удаленных точек и блоков, объем, число импортированных и пропущенных точек. Исторический результат успешного бэкапа сохраняется после удаления его данных; доступность точки отмечается отдельно.

Медиасервер дополнительно сохраняет собственный аудит в `audit/`, включая начало и исход изменений, с ID операции управления. Он остается доступен при потере центрального каталога:

```sh
bin/srk --config .local/media.json --json media repository audit
```

При потере подтверждения обслуживания нужно проверить этот аудит и `maintenance/`, а не считать ошибку соединения доказательством отсутствия изменений.

## Текущие границы

Импорт относится к дисковому формату СРК версии 1. Ленточный импорт, сторонние форматы, сохранение ACL/xattr/UID/GID, прикладные снимки и PostgreSQL/WAL этим этапом не добавляются. Полная проверка предварительного плана читает содержимое всех точек и может занимать существенное время на больших репозиториях. Поврежденный манифест блокирует очистку до диагностики; он не удаляется автоматически как «ненужный».
