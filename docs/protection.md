# Контроль защищённости 3-2-1

Веб-интерфейс: **«Защита 3-2-1»**. Карточка объединяет оригинал, резервные копии, реплики и результаты восстановления. Оценка выполняется при открытии и по кнопке обновления; фоновые уведомления пока не реализованы.

## Настройка

1. Добавьте площадки в «Площадки и хранилища». Поле disaster_domain обозначает общую зону аварии: два помещения одного здания должны иметь одинаковое значение, если одна авария может затронуть оба.
2. Добавьте хранилища с фактическими идентификаторами и площадками:
   - repository: ID медиасервера и UUID репозитория. UI подставляет UUID из каталога выбранного медиасервера.
   - tape: ID медиасервера, библиотеки и штрихкод конкретной кассеты.
   - flash: ID медиасервера и UUID файловой системы съёмного накопителя, а не имя его конфигурационного профиля.
   - longhorn: описательная запись внешнего backupstore; её затем нужно явно связать с заданием.
3. Укажите тип носителя и failure_domain. Все пути, LUN и репозитории на одном общем backend должны иметь один домен отказа. Разные имена медиасерверов не доказывают независимость.
4. В карточке задания откройте «Требования защиты»: площадка и тип носителя оригинала, домен отказа источника, RPO в часах, максимальный возраст проверки восстановления. Для Longhorn выберите фактически используемый backupstore.

Местоположение, физический тип носителя и общие домены отказа задаёт администратор: география оборудования автоматически не определяется. Оригинал считается одной настроенной рабочей копией; доступность исходного приложения этим расчётом не проверяется. Изменение настроек не перемещает данные. Удаление настройки не удаляет копии; связанные настройки сначала нужно перепривязать.

## Условия статуса «Защищено»

- Минимум две резервные копии в разных доменах отказа, не совпадающих с доменом оригинала.
- Минимум два типа носителей с учётом оригинала.
- Полная копия в другой зоне аварии, а не только на площадке с другим названием.
- Возраст доступной точки соответствует RPO; две обязательные независимые копии также укладываются в RPO.
- Свежий успешный результат восстановления; более поздняя неуспешная попытка не скрывается старым успехом.
- История и настройки достаточны для расчёта.

Несколько снимков в одном хранилище не увеличивают число независимых копий. Реплики связаны с исходным заданием через происхождение, а не названия. Импорт учитывается при сохранённом происхождении и подтверждённой проверке. Неизвестная связь с исходным заданием не угадывается.

## Подтверждение наличия

Менеджер читает текущий каталог дисковых репозиториев через mTLS и сопоставляет его с успешными подтверждёнными операциями. Срок хранения и hold берутся с медиасервера. Старый успешный запуск не заменяет наличие манифеста в текущем каталоге. Повторная хеш-проверка всех блоков при открытии страницы не запускается; учитывается ранее полученное подтверждение целостности.

Для лент проверяются каталог копий, верификация, срок/hold, отсутствие незавершённого стирания и физическое обнаружение штрихкода в SCSI-инвентаризации. Ленточный эмулятор не подтверждает производственную защиту. Для flash нужен подключённый накопитель с соответствующим UUID и известным каталогом. Недоступные офлайновые носители не подтверждают текущую доступность и удалённость автоматически. Аттестация вывоза и хранения офлайновых носителей — будущий этап.

На опрос медиасервера выделено до 5 секунд, всего отчёта — до 15 секунд; параллельно опрашиваются не более четырёх серверов. Ошибка или тайм-аут означает отсутствие подтверждения, а не доказанное физическое отсутствие копии. При истории более 50 000 операций зелёный статус запрещён и показано ограничение полноты.

## RPO и восстановление

RPO рассчитывается по времени данных исходной копии. Завершение репликации не «омолаживает» данные: используется captured_at. Отставание удалённой копии — разница между самой свежей доступной точкой и самой свежей подтверждённой удалённой копией. Возраст удалённой копии также сравнивается с RPO.

Для PostgreSQL используется возраст базовой точки, без улучшения за счёт непрерывного WAL. Это консервативная оценка, а не расчёт предельного RPO по WAL/PITR. Нативные индикаторы WAL/PITR остаются в своих разделах.

Для обычных заданий учитывается успешное восстановление с verified=true. Оно не означает проверку всех функций приложения; VM-проверка может подтверждать только управляющий API. Для Kubernetes/Longhorn нужны плановые прикладные проверки: passed, успешная очистка, покрытие всех namespaces и свежесть результатов. JSON-экспорт или подготовка ресурсов без прикладного теста не считаются проверкой приложения. Отменённая до запуска проверка не заменяет выполненный тест.

## Longhorn

JSON-архив содержит объекты и backup handles; блоки PVC остаются во внешнем backupstore. Две реплики JSON или кассета с метаданными не превращаются в две независимые копии PVC.

Количество копий метаданных показывается отдельно. Набор «метаданные + внешний backupstore» учитывается максимум один раз и только при настроенной зависимости и свежих успешных прикладных проверках **этой же копии на том же медиасервере для всех namespaces**. Для удалённости набора вне зоны аварии должны находиться и метаданные, и объявленный backupstore. Фактическую привязку и размещение backupstore задаёт администратор; по handle география не определяется.

Текущая интеграция не подтверждает вторую независимую копию блоков Longhorn, поэтому несколько реплик метаданных не дают зелёный статус 3-2-1. Архив Kubernetes без подтверждённых данных PVC также не считается полной защитой приложения.

## API и CLI

- GET /v1/protection — время оценки, настройки, карточки, обнаруженные репозитории и ошибки инвентаризации.
- GET /v1/protection/settings — настройки и version.
- PUT /v1/protection/settings — полная замена настроек с текущей version; устаревшая версия получает HTTP 409. Требуются административные права, изменения записываются в аудит.

Команды:

    srk --config /etc/srk/admin.json --json manager protection report
    srk --config /etc/srk/admin.json --json manager protection settings > protection.json
    srk --config /etc/srk/admin.json manager protection put --file protection.json

Структура настроек: version, sites, storages, policies. Site: id/name/disaster_domain. Storage: id/name/kind/medium_type/site_id/failure_domain и идентификаторы media_id/repository_id/library_id/barcode/volume_id по типу. Policy: job_id/source_site_id/source_medium_type/source_failure_domain/rpo_seconds/restore_max_age_seconds и необязательный longhorn_storage_id.

Если все фактические носители являются дисками, требование разных типов не выполнено. Не меняйте тип в настройках ради зелёного статуса.
