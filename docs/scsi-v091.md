# Linux SCSI и медиасервер

Медиасервер принимает `tape.backend: scsi`. Linux SG_IO выполняет INQUIRY/VPD, MODE SENSE, READ ELEMENT STATUS, MOVE MEDIUM, REWIND, SPACE FILEMARKS, READ/WRITE, ERASE и синхронный WRITE FILEMARKS. Серийные номера устройств должны совпадать с конфигурацией. Привод должен быть настроен в variable-block mode; СРК проверяет режим и защиту записи, но не изменяет настройки привода автоматически.

Пример фрагмента конфигурации media (адреса элементов и serial заменяются фактическими):

```json
{
  "tape": {
    "backend": "scsi",
    "library_id": "TS4300",
    "drives": ["DRIVE1"],
    "cartridges": [{"barcode":"SRK001L9","slot":100,"generation":9,"capacity_bytes":18000000000000}],
    "scsi": {
      "changer": {"path":"/dev/sg2","serial":"CHANGER-SERIAL"},
      "transport_element": 1,
      "drives": {"DRIVE1":{"path":"/dev/sg3","serial":"DRIVE-SERIAL","element":200}}
    }
  }
}
```

Нельзя использовать один адрес для робота, привода и слота. Путь устройства должен вести к character device; открытие эксклюзивное. Права ОС и systemd должны разрешать сервису доступ к заданным устройствам. Не запускайте параллельно другие программы управления той же библиотекой.

## Операции и формат

Доступны load, unload, первичная label пустой кассеты, write, verify, restore, import, erase, recycle и recover. API capabilities и поле actions инвентаризации перечисляют доступные действия. Веб-интерфейс скрывает неподдерживаемые операции. Изменение hold уже записанного физического архива пока не поддерживается; удержание, заданное при записи, сохраняется при импорте и блокирует стирание.

Файл 0 содержит метку SRKSCSI1 и UUID носителя; последующие файлы — самостоятельные архивы SRKTAPE1. Перед записью проверяется физическая метка. Архив сначала подготавливается на диске media, затем пишется на ленту и полностью перечитывается с проверкой SHA-256. Требуется место для staging и контрольного чтения. При восстановлении данные читаются с физического устройства, даже если staging сохранился.

```sh
srk --config /etc/srk/admin.json --endpoint https://media.example.org:8444 media tape capabilities
srk --config /etc/srk/admin.json --json manager tape inventory MEDIA_ID
srk --config /etc/srk/admin.json --wait manager tape load MEDIA_ID SRK001L9 --drive DRIVE1
srk --config /etc/srk/admin.json --wait manager tape label MEDIA_ID SRK001L9 --label 'Архив 01' --reason 'Первичная маркировка' --confirm-barcode SRK001L9
srk --config /etc/srk/admin.json --wait --timeout 12h manager tape write MEDIA_ID SRK001L9 --run RUN_ID --retention-days 30
srk --config /etc/srk/admin.json --wait --timeout 12h manager tape restore MEDIA_ID SRK001L9 --copy COPY_ID --agent AGENT_ID
```

## Позиция и восстановление после сбоя

Состояние находится в `repository/tape-scsi`. `scsi-index.json` сохраняет подтверждённый порядок файлов и отдельные незавершённые намерения по приводам (`pending_by_drive`). Старый журнал с одним `pending` автоматически переносится при открытии. `position-journal` хранит последнее состояние каждой операции с номером файла, кассетой, приводом, исходным и целевым элементами роботики, временем и ошибкой. `scsi-operations` содержит квитанции, привязанные к ID операции и исходному запросу. Повтор завершённого запроса возвращает квитанцию без повторной записи; изменение параметров с прежним ID отклоняется.

В интерфейсе «Кассеты и библиотека» показаны последние 20 записей журнала позиции. Полная история сохраняется на медиасервере. При неподтверждённом результате блокируются новые операции на соответствующем приводе и кассете. Неопределённый результат роботики блокирует новые перемещения. Команда сверки:

```sh
srk --config /etc/srk/admin.json --wait --timeout 12h manager tape recover MEDIA_ID SRK001L9 --drive DRIVE1
```

После потери ответа MOVE сверка подтверждает кассету в ожидаемом целевом элементе. После маркировки сверяет физическую метку. После записи перечитывает записанный файл и подтверждает индекс без повторной записи. Если кассета находится в другом месте или файл неполон/повреждён, блокировка сохраняется. Не удаляйте журналы и не пытайтесь обойти блокировку новой записью. Автоматического исправления частично записанного файла нет.

Длительные операции разных приводов выполняются параллельно. Роботика выполняется последовательно: чтение положения, MOVE и подтверждение результата защищены общей блокировкой. Опрос инвентаризации не ждёт завершения записи или чтения ленты, но может ждать перемещения робота; текущий этап доступен через API прогресса media. Отмена контекста не прерывает уже выполняющийся ioctl; результат определяется после возврата команды. Ошибки записи не повторяются автоматически.

## Проверки реализации

Командный сценарий охватывает потерю ответа роботики и маркировки, перезапуск backend, запись с потерянным readback, блокировку новой записи, восстановление позиции без повторной записи, восстановление после удаления staging, повтор квитанции и обнаружение физического повреждения. Реальное оборудование IBM не подключалось; аппаратная квалификация отдельно от функциональности программного транспорта.

## Импорт и безопасная подготовка к перезаписи

`import` читает физическую метку и все архивы до конца записанных данных. Проверяются UUID носителя, штрихкод, идентификаторы архивов и контрольные суммы. Каталог публикуется только после полного успешного чтения. Повреждённый или неизвестный файл блокирует публикацию. Нужен свободный staging объёмом до занятого пространства кассеты. Импорт на другом медиасервере восстанавливает каталог и сроки хранения из архивов; более строгие локальные сроки и удержания сохраняются.

```sh
srk --config /etc/srk/admin.json --wait --timeout 12h manager tape import MEDIA_ID SRK001L9
srk --config /etc/srk/admin.json --wait --timeout 12h manager tape erase MEDIA_ID SRK001L9 --mode long --reason 'Истекли сроки хранения' --confirm-barcode SRK001L9
srk --config /etc/srk/admin.json --wait --timeout 12h manager tape recycle MEDIA_ID SRK001L9 --reason 'Повторное использование' --confirm-barcode SRK001L9
```

Перед ERASE выполняется полное контрольное чтение кассеты и повторная проверка сроков. Неизвестный каталог, действующие копии, hold, WORM и аппаратная защита записи запрещают стирание. Тип носителя проверяется через MODE SENSE: допускаются перезаписываемые LTO-8/9. Оператор указывает причину и подтверждает штрихкод.

`erase --mode quick` и `recycle` выполняют короткий ERASE с записью EOD; это не гарантирует физическое уничтожение прежних данных. `erase --mode long` отправляет синхронный ERASE LONG. После операции создаётся новый UUID тома, записывается и перечитывается метка, проверяется отсутствие последующих файлов. Логическая метка и штрихкод сохраняются.

Если ответ ERASE потерян, `recover` не повторяет разрушительную команду: проверяет готовность привода, пустое начало либо ожидаемую новую метку и конец данных. Неоднозначное состояние оставляет соответствующий привод и кассету заблокированными. Сверка подтверждает пригодность для повторной записи, а не сертифицированное уничтожение данных. После сбоя предварительного чтения сверка повторяет только импорт; стирание нужно запросить отдельно.

Прогресс импорта сообщает этап, число проверенных файлов и байты; общий процент до обнаружения конца данных неизвестен. ERASE выполняется внутри накопителя без искусственного процента. Журнал позиции и история задания доступны в интерфейсе.

## Очередь и параллельные приводы

Каждый привод выполняет одну операцию. Задания на разные приводы могут выполняться одновременно; очередь одного привода сохраняет порядок поступления. Одновременно резервируется кассета, чтобы её не выгрузили во время записи. Перед выполнением проверяется фактическое расположение: если кассета сменила привод, операция отклоняется, а не выполняется на незарезервированном устройстве. Выбор свободного привода и автоматическая смена кассет не выполняются: сначала загрузите кассету командой `load --drive`.

Менеджер сохраняет задания в PostgreSQL и учитывает `max_parallel` и `per_media`; для двух параллельных приводов оба лимита должны быть не меньше 2. Очередь на занятый привод не занимает дополнительный слот менеджера, если указан его ID. Для загруженной SCSI-кассеты менеджер определяет ID по инвентаризации при приёме запроса. Медиасервер дополнительно резервирует привод и кассету, защищаясь от конкурентных запросов. Ожидание можно отменить до начала выполнения; ресурсы очереди освобождаются без обращения к ленте.

```sh
srk --config /etc/srk/admin.json --json manager tape queue MEDIA_ID
srk --config /etc/srk/admin.json --wait --timeout 12h manager tape write MEDIA_ID SRK001L9 --drive DRIVE1 --run RUN_ID --retention-days 30
```

Вторая запись на другой привод запускается отдельным заданием. В окне библиотеки показаны очередь, состояния приводов, текущий этап, прогресс и последние 50 завершённых операций. Кнопка «Прогресс и журнал» открывает историю задания. Ожидающее задание можно отменить. Числовой процент записи и контрольного чтения относится к текущему этапу; 100% успешной операции выдаётся после подтверждения. Для ERASE и перемещения, которые не сообщают число обработанных байтов, показывается этап без выдуманного процента.

API: `GET /v1/media/{media}/tape/queue` возвращает текущие задания и последние 50 завершённых. Инвентаризация содержит `positions` для всех неподтверждённых приводов и `queue` для принятых медиасервером запросов. Поле `position` сохранено для совместимости и содержит первое намерение. Полная история заданий и событий хранится в каталоге менеджера.

После перезапуска ожидающие задания остаются в каталоге менеджера. Выполнявшиеся физические операции не повторяются автоматически: результат сверяется с журналом привода через `recover`. Сбой одного привода не останавливает чтение и запись на остальных. Временные файлы контрольного чтения и стирания разделены по кассетам, индекс обновляется под короткой блокировкой без удержания её во время I/O.

## Пулы и автоматический цикл записи

Пул задаёт ID, название, список кассет и разрешённых приводов. Кассета принадлежит одному пулу; приводы могут использоваться несколькими пулами. Пулы сохраняются на медиасервере в `pools.json`, редактируются через менеджер с аудитом, CLI или окно библиотеки.

```json
{"id":"DAILY","name":"Ежедневные копии","barcodes":["SRK001L9","SRK002L9"],"drives":["DRIVE1","DRIVE2"]}
```

```sh
srk --config /etc/srk/admin.json manager tape pool-set MEDIA_ID /etc/srk/daily-pool.json
srk --config /etc/srk/admin.json --wait --timeout 12h manager tape archive MEDIA_ID DAILY --run RUN_ID --retention-days 30
```

Автоматическое задание выбирает известную маркированную кассету с достаточным свободным пространством и свободный совместимый привод, загружает кассету, записывает и проверяет архив, затем выгружает в слот. Привод и кассета резервируются на весь цикл, включая промежутки между роботикой и записью. Два задания могут выбрать разные приводы одного пула.

Подбор использует консервативную оценку размера: логические файлы плюс метаданные. Архив должен целиком помещаться на одной кассете; spanning не реализован. Неизвестные, WORM, защищённые, занятые или неподтверждённые носители исключаются. Действующие копии не стираются: запись дописывает новый архив, если места достаточно. Подготовку истёкших кассет к перезаписи и первичную маркировку оператор выполняет явно.

Если нет подходящей кассеты или привода, задание сообщает `tape-waiting-media` и периодически повторяет подбор. Оператор может маркировать/освободить носитель, изменить пул либо отменить ожидание. Действует общий тайм-аут менеджера 12 часов и лимиты параллельности. Ожидание уже отправленного на media задания занимает слот менеджера; оставляйте дополнительный слот для ручных операций либо отмените ожидающее задание перед обслуживанием. UI показывает очередь и свободную ёмкость носителей пула; суммарная ёмкость не означает, что один архив поместится на одну кассету.

В `pool-operations` сохраняется квитанция всего цикла; шаги имеют стабильные отдельные ID и собственные журналы. Завершённый запрос не пишет копию повторно. Незавершённый цикл после перезапуска автоматически не переигрывается: сначала проверьте инвентаризацию/журнал и выполните необходимый `recover`. При сбое выгрузки уже записанная копия может быть исправна; перед новым заданием проверьте каталог, чтобы не создавать ненужный дубль.

API настройки: `PUT /v1/media/{media}/tape/pools/{pool}`. Автоматическая запись: обычный POST операций с `action: write`, `pool_id`, `snapshot_id` (ID успешного задания на менеджере), `retention_days`, без `barcode` и `drive_id`.
